01
빈 칸
Gaps · 측정 못 한 것
Retrieval 분리 평가를 못했습니다
end-to-end만 측정. 개선이 검색에서 왔는지 생성에서 왔는지 귀속이 어렵습니다. → Recall@K / MRR 라벨링이 자기 검증 트랙 01
서버 2차 방어의 효과를 계측 못 했습니다
_REFUSAL_PATTERNS가 얼마나 발동했고, 그 중 실제 환각이 몇 %인지 모릅니다. → false positive / false negative 분리 측정 필요
유사 질문 캐시 threshold 0.95는 경험값입니다
hit rate와 false hit를 threshold별로 측정하는 튜닝 작업을 아직 안 했습니다. → threshold 0.85 / 0.90 / 0.95 / 0.99 비교
02
과소평가
Under-estimated · 있는데 약하게 말한
Semantic Cache는 이미 구현됐습니다
Chroma cache_questions 컬렉션 + cosine 0.95로 의미 유사까지 잡습니다. → "정확 일치만"이 아니라 "3단계 캐시 이미 작동"
v3 프롬프트의 Claude Refusal은 100%입니다
v2(83%) 기준으로 "UX로 골랐다"고 하면 약해집니다. v3 기준으로는 지표에서도 대부분 우세. → "UX + 지표 이중 축"으로 프레임
section_path 메타데이터는 이미 보존합니다
"상위 > 하위" 계층 경로가 모든 청크에 붙어 있어, 출처 추적 정확도가 먼저 잡힌 상태입니다. → Parent-doc retrieval 도입 시 기반 이미 마련
03
잘못 본 프레임
Wrong Framing · 고쳐 말해야 할
"비용 vs 성능"은 BGE-M3에 맞지 않습니다
오픈소스 셀프 호스팅이라 API 과금이 없습니다. 진짜 트레이드오프는 인프라 비용 vs 검색 품질. → "온프렘 + 확장성"으로 프레이밍
"UX로 골랐다"는 방어가 약합니다
v3 이후 Retrieval · Citation · Refusal 모두 우세인데, UX 단일 축으로 설명하면 면접관 반박 여지. → "지표 동률~우세 + UX 가산점"
"Agentic RAG 안 함"이 아니라 "안 한 이유가 있다"입니다
측정 없이 복잡도 추가하면 PoC 신뢰도가 오히려 흔들립니다. Query Router부터 단계적 도입이 다음. → 의도적 범위 밖 + 단계적 로드맵
