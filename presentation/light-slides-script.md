### 스크립트
> "첫 번째 고민은 LLM 선택이었습니다. 과제는 Claude SDK와 Codex CLI 중 택 1이었지만, **온프렘 시나리오에서는 둘 다 못 쓰는 상황**을 고려해 처음부터 LLMProvider 인터페이스로 추상화했습니다. 호출 측 코드는 어떤 모델인지 모릅니다.
>
> Claude와 Codex 두 구현체를 50개 골든 데이터셋과 7개 메트릭으로 비교했는데, 여기서 핵심은 **v2에서 v3로 가는 튜닝 여정** 입니다.
>
> v2 시점에서는 Claude의 Refusal 정확도가 83%였습니다. '문서에 없으면 모른다고 답하라'는 지시를 종종 무시하고 억지 답을 만들었습니다. 이때까지는 환각 억제에서 Codex가 우세했습니다.
>
> v3에서 세 가지를 바꿨습니다 — Few-shot 예시 2개 추가, '확인할 수 없습니다' 같은 동의어 사용 금지, 서버 단에 10종 거절 패턴 매칭. 이 후 Claude의 Refusal이 100%에 도달했고, Retrieval과 Citation에서도 Codex를 7%p 앞섰습니다.
>
> Codex가 v3 기준으로 우세한 건 Latency뿐인데, SSE 스트리밍과 3단계 캐시(히트 시 0ms)로 체감 지연을 상쇄하고, 답변 구조화 UX(번호·불릿·볼드)까지 고려해 Claude를 기본 모델로 확정했습니다.
>
> 다만 50건 + 단일 평가자라는 모수 한계는 분명합니다. 그리고 **온프렘 전환 시 Ollama + Qwen2.5-7B로 가야 하는데**, 그 어댑터는 아직 미구현이고 — 마지막 슬라이드의 검증 트랙 ③에서 다시 다루겠습니다."

**전달 포인트:**
- **v2→v3 튜닝 서사가 이 슬라이드의 심장.** "데이터로 의사결정한다"는 메시지.

## Slide 04 — 고민 ② 임베딩 & 청킹 (2:30)

### 슬라이드 내용
**임베딩: BGE-M3**
- 한·영 혼재 사내 문서에 안정적 (MTEB Korean 상위)
- 온프렘 가능, API 과금 없음
- Dense + Sparse + 8K context 단일 모델 (현재 Dense만 활용)

**청킹: 문서 타입별 분기** (`app/chunking/router.py`)
- **Markdown** — 헤더 기반 분할 + 상위 헤더 경로 메타데이터 (`"정책 안내 > 교육비 지원"`)
- **PDF** — pypdf 추출 → 번호 헤더 감지 → 마크다운 변환 후 동일 파이프라인 (TS-006)
- **공통** — 400자 초과 시 재귀 분할, overlap 80자

**핵심 인사이트** — "더 많은 정보 ≠ 더 좋은 검색" (LlamaParse 실험: 100% → 80%)

### 스크립트
> "두 번째 고민은 임베딩과 청킹입니다.
>
> 임베딩은 BGE-M3를 골랐습니다. 한국어와 영어가 섞인 사내 문서에 안정적이고, 온프렘 배포가 가능하며, Dense·Sparse·Long-context를 단일 모델로 지원합니다. 다만 **현재는 Dense만 쓰고 있어** 모델 가치의 일부만 활용 중입니다.
>
> 여기서 한 가지 미리 공유드릴 인사이트가 있는데 — **온프렘 RAG에서 임베딩 모델 업그레이드는 의외로 ROI가 낮습니다**. BGE-M3에서 더 큰 모델로 바꿔도 Recall@10이 보통 2~5%p만 오릅니다. 같은 자원으로 더 큰 효과를 보는 곳은 **검색 후단(hybrid search + reranker)** 인데, 이건 Phase III 한계 슬라이드에서 다시 다루겠습니다.
>
> 청킹은 문서 구조가 의미 단위를 결정한다는 가정 위에서 타입별로 분기했습니다. Markdown은 헤더 기반 분할에 **상위 헤더 경로를 메타데이터로** 함께 저장합니다 — 예를 들어 '교육비 연 100만원'이라는 청크에 '정책 안내 > 교육비 지원'이라는 경로가 붙어서, 검색 결과에서 어느 맥락의 100만원인지 구분이 됩니다.
>
> PDF에서 흥미로운 발견은 — pypdf로 추출 후 번호 헤더를 감지해 마크다운으로 변환하는 단계를 추가했더니, 동일 청크 수에서 섹션 메타데이터가 빈 문자열에서 실제 헤더 경로로 바뀌었고 속도도 22% 개선됐습니다.
>
> 청킹 실험에서 **반례 한 가지가 흥미로웠습니다** — LlamaParse라는 더 정교한 PDF 파서를 써봤더니 정확도가 100%에서 80%로 떨어졌습니다. 더 깨끗한 추출이 항상 더 좋은 검색을 보장하지 않더라는 것 — 청크 경계와 임베딩 모델의 정합성이 더 중요했습니다."

**전달 포인트:**
- 임베딩 모델 업그레이드 ROI 낮다는 인사이트는 **Phase III에서 hybrid/reranker 우선순위로 회수.**
- "더 많은 정보 ≠ 더 좋은 검색" 반례 — 실험과 학습의 흔적을 보여줌.

## Slide 05 — 고민 ③ 3단계 캐시 (2:00)

### 슬라이드 내용

| 단계 | 구현체 | 키 / 방식 | 코드 위치 |
|---|---|---|---|
| ① 정확 일치 | Redis | SHA-256(question), TTL 1시간 | `redis_cache.py` |
| ② **유사 질문** | **Chroma `cache_questions` 컬렉션** | 질문 임베딩 → **cosine ≥ 0.95** | `cache_service.py:68` |
| ③ 무효화 | 문서 업로드 시 전체 QA 캐시 삭제 | `answerable=false` 미저장 (좀비 방지) | `cache_service.py` |

**실측 효과**
- Cache miss (RAG 전체 실행): **~13.6초** → **154ms** (정확) / **0ms** (유사)

### 스크립트
> "세 번째 고민은 캐시 설계입니다. 3단계 모두 이미 구현되어 동작합니다.
>
> 1단계는 Redis에 질문 SHA-256 해시를 키로 한 정확 일치 캐시입니다.
>
> 2단계가 핵심인데, **Semantic Cache** 입니다. 별도 도구 없이 Chroma에 `cache_questions`라는 컬렉션을 하나 더 두고, 질문 임베딩의 cosine 유사도가 0.95 이상이면 히트로 판정합니다. '교육비 지원 금액이 얼마인가요?'와 '교육비 한도가 얼마죠?'를 같은 질문으로 인식합니다.
>
> 3단계는 무효화입니다. 문서 업로드 시 전체 QA 캐시를 삭제합니다. 파일별 추적이 아닌 전체 삭제를 택한 이유는 **'좀비 캐시' 엣지 케이스** 때문입니다 — 문서가 없을 때 '찾을 수 없다'고 답한 캐시는 어떤 파일과도 연관이 없어서, 나중에 관련 문서를 업로드해도 무효화되지 않습니다. 그래서 `answerable=false` 응답 자체를 캐시에 저장하지 않고, 문서 변경 시엔 전체 무효화하는 단순한 원칙을 택했습니다.
>
> 다음 단계는 **threshold 0.95의 정량 튜닝** 입니다. 현재는 경험적 값이고, threshold별 hit rate와 false hit를 측정하는 작업이 남아 있습니다."

**전달 포인트:**
- **Semantic Cache가 차별화 포인트.** 많은 PoC가 정확 일치만 구현.
- 좀비 캐시 → 설계 사고 과정을 보여주는 좋은 사례.

## Slide 06 — 고민 ④ "모른다"고 말하게 만들기 (2:00)

### 슬라이드 내용
**Layer 1 — 프롬프트 레벨**
- 정확한 거절 문장 강제: 「제공된 문서에서 해당 내용을 찾을 수 없습니다」
- Few-shot 예시 2개 (답변 가능 + 답변 불가)
- 동의어 사용 금지 (v3 추가)
- citation 형식 강제 (JSON schema)

**Layer 2 — 서버 단 검증** (`rag_service.py:18`)
- `_REFUSAL_PATTERNS` **10종** 거절 패턴 매칭
- LLM이 동의어로 거절해도 포착
- `answerable=false` 응답은 출처 차단 + 캐시 미저장

**튜닝 효과: Refusal v2 83% → v3 100%**

### 스크립트
> "네 번째 고민, 어쩌면 가장 중요한 환각 억제입니다. 두 레이어로 구현했습니다.
>
> 1차는 프롬프트 레벨입니다. '문서에서 근거를 찾지 못하면 정확히 이 문장으로 답하라'를 강제하고, v3에서는 동의어 사용 금지와 Few-shot 예시를 추가했습니다.
>
> 2차는 서버 단 검증입니다. LLM이 지시를 완벽히 따르지 않을 때를 대비해, **10가지 거절 패턴을 코드 레벨에서 한 번 더 매칭** 합니다. 실제로 프롬프트에 동의어 금지를 명시했는데도 Claude가 종종 우회하는 케이스가 있었고, 서버가 그걸 거절로 인식 못하면 `answerable=true`로 오판정되어 근거 없는 답변이 출처까지 표시되는 문제가 있었습니다. (TS-009 트러블슈팅 사례)
>
> 이 이중 방어 덕분에 v2의 Refusal 83%가 v3에서 100%로 올라왔습니다.
>
> **현재 구현의 가장 큰 빈 칸은 서버 단 체크의 발동률·적중률 계측입니다**. 즉 '프롬프트만으로 충분한데 서버 체크가 안전장치일 뿐인지, 실제로 프롬프트 실패를 구제한 케이스가 얼마나 되는지'를 모릅니다. Phase III 한계 슬라이드의 우선순위 2번입니다."

**전달 포인트:**
- "지시는 LLM에게 확률적이다, 검증은 결정적 코드로" — 핵심 교훈.
- 발동률 미측정은 먼저 인정 + 한계 슬라이드로 self-reference.

## Slide 07 — 시스템 한 장 (2:00)

### 슬라이드 내용
**Ingest 파이프라인**
```
Upload (PDF/TXT/MD) → Extract (pypdf+md) → Chunk (타입 분기)
  → Embed (BGE-M3) → Store (ChromaDB)
```

**Query 파이프라인**
```
Question → 3단계 캐시 → Retrieve (cosine) → LLM (+ 환각 방어)
  → Answer (SSE stream)
```

**핵심 설계 3가지**
1. LLMProvider 추상화 (provider 교체 가능)
2. 환각 이중 방어 (프롬프트 + 서버)
3. 문서 타입별 청킹 + 헤더 경로 메타데이터

### 스크립트
> "지금까지 풀어드린 네 가지 고민이 어떻게 코드로 떨어졌는지, 한 장으로 묶어 보여드립니다.
>
> 위쪽은 Ingest 파이프라인 — 문서가 들어오면 추출, 청킹, 임베딩, 저장의 5단계를 거칩니다.
>
> 아래쪽은 Query 파이프라인 — 질문이 들어오면 3단계 캐시를 먼저 확인하고, 미스 시 검색 → LLM 호출 → 환각 방어를 거쳐 SSE로 스트리밍합니다.
>
> 이 한 장에서 강조드릴 세 가지 설계 선택은 — 첫째 LLMProvider 추상화로 모델 교체 가능성, 둘째 환각의 이중 방어, 셋째 문서 타입별 청킹과 헤더 경로 보존입니다.
>
> 이제 실제로 동작하는 모습을 데모로 보여드리겠습니다."

**전달 포인트:** Phase I의 4가지 고민이 한 그림에 수렴되는 순간. 다음 슬라이드(데모)로의 자연스러운 전환.

## Slide 09 — Naive RAG가 아닌 이유 (1:30)

### 슬라이드 내용
**이미 구현된 Advanced 4가지** — 과제 제출 후 재발견

| 요소 | 구현 | 코드 위치 |
|---|---|---|
| 상위 헤더 경로 보존 | 청크 메타데이터에 `section: "정책 > 교육비 지원"` | `chunking/markdown.py:40` |
| Semantic Cache | Chroma 별도 컬렉션 + cosine ≥ 0.95 | `cache_service.py:68` |
| `answerable=false` 캐시 미저장 | 좀비 캐시 방지 | `rag_service.py:89` |
| 7메트릭 평가 하네스 | 50개 골든셋 + NoOpCacheService | `eval/metrics.py` |

### 스크립트
> "여기서부터 Phase III, 프로덕션 관점에서 본 보완점입니다. 시작은 의외로 긍정적인 발견입니다.
>
> 발표를 준비하면서, 제 구현에 이미 들어 있지만 정리가 안 됐던 Advanced RAG 요소 네 가지를 재발견했습니다.
>
> 첫째, 마크다운 청킹의 **상위 헤더 경로 메타데이터**. 둘째, **Semantic Cache** — cosine 0.95 기반 유사 질문 매칭. 셋째, **답변 불가 응답을 캐시에 저장하지 않는** 설계 — 좀비 캐시 방지. 넷째, **7메트릭 평가 하네스** — `NoOpCacheService`로 순수 LLM 성능을 분리 측정하는 구조까지 갖춰져 있습니다.
>
> 이 네 가지는 의도적으로 설계한 것도 있고, 트러블슈팅 과정에서 필요에 의해 추가한 것도 있습니다. 결과적으로 Naive RAG에서 한 단계 올라간 부분이고, **정리하면서 다시 가치를 인식하게 됐습니다**.
>
> 이 슬라이드의 의미는 단순한 자랑이 아닙니다 — 다음 슬라이드의 OfficeAgent와 비교할 때, 출발선이 어디인지를 정확히 짚어두기 위해서입니다."

**전달 포인트:**
- **"이미 있는 것을 자랑"** — 새 기능 추가 없이 ROI 가장 높은 슬라이드.
- 마지막 한 줄로 다음 슬라이드 연결 — "출발선을 정확히 짚는다."

## Slide 10 — OfficeAgent와의 비교 (2:30)

### 슬라이드 내용

| 영역 | OfficeAgent | 본 PoC | 격차 해소 방향 |
|---|---|---|---|
| RAG 방식 | Agentic RAG | Naive + Advanced 일부 | Query Router부터 단계적, **LangGraph 검토** |
| 접근 제어 | RBAC | 미구현 | Vector DB 메타데이터 필터링 |
| 민감정보 | 자동 마스킹 | 미구현 | 정규식 PoC → presidio |
| 배포 | SaaS / 공공 / 온프렘 | 로컬 PoC | LLMProvider 위에 Ollama 어댑터 |
| 평가 | — | 50×7 메트릭 자산 | (PoC 강점) |

### 스크립트
> "OfficeAgent와 직접 비교해보겠습니다. 같은 문제 — **환각 억제된 사내 문서 Q&A** — 를 푸는데, 축이 다릅니다.
>
> OfficeAgent는 **Agentic RAG** 를 핵심 가치로 내세웁니다. 제 구현은 Naive RAG에서 시작해 Advanced 요소를 일부 도입한 수준입니다. Agentic은 의도적으로 범위 밖에 두었습니다 — Query Router나 Self-correction 루프는 LLM 호출 비용·지연·복잡도를 추가하는데, 그게 실제 품질 개선으로 이어지는지를 측정 없이 도입하면 PoC의 신뢰도를 해친다고 판단했습니다.
>
> 다만 Agentic RAG로 확장하는 시점에는 **LangGraph 도입을 검토할 계획** 입니다. Query Router, Self-Reflective RAG, Multi-hop 검색 같은 패턴은 본질적으로 **조건부 분기와 루프가 있는 상태 기계** 인데, 직접 if/else로 짜면 코드 품질이 빠르게 저하되는 영역입니다. 반대로 현재 PoC처럼 직선 파이프라인에서는 LangChain 같은 프레임워크의 추상화 비용이 가치보다 커서 의도적으로 직접 구현했습니다 — 이게 면접 질문이 나올 수 있는 지점이라 미리 짚어둡니다.
>
> RBAC와 민감정보 자동 마스킹은 OfficeAgent가 프로덕트로 해결한 영역이고, 제 PoC에는 없습니다. 솔직히 범위에 넣지 못한 부분입니다. RBAC는 vector DB 메타데이터 필터링으로 1차 구현이 가능하고, 마스킹은 정규식 기반 PoC에서 시작해 presidio로 확장하는 경로를 생각하고 있습니다.
>
> 온프렘 배포는 LLMProvider 추상화 덕에 Claude 의존성을 Ollama 계열로 교체 가능한 **구조** 이지만, 실제 어댑터 구현과 측정은 아직입니다.
>
> **PoC의 강점이 하나 있다면 평가 자산** 입니다. 50개 골든셋과 7메트릭 하네스는 OfficeAgent가 이 단계에서 갖췄을지 알 수 없는 부분이고, 새 컴포넌트를 도입할 때마다 효용을 정량적으로 비교할 수 있는 기반입니다."

**전달 포인트:**
- "Agentic RAG를 왜 안 했는가"가 가장 중요한 방어 — *"안 했다"* 가 아니라 *"근거가 있다"*.
- LangChain/LangGraph 언급은 면접관 입장에서 "트레이드오프 인지" 신호로 해석됨.
- OfficeAgent를 깎지도, 무조건 띄우지도 않기.

## Slide 11 — 한계와 다음 단계 (2:00)

### 슬라이드 내용
**7개 한계 (프로덕트 영향도 우선순위)**
1. Retrieval 분리 평가 미수행 — gold passage 라벨링 → Recall@K, MRR 측정
2. 서버 단 2차 환각 체크의 발동률·적중률 계측 부재
3. PDF 파서의 표/레이아웃 한계 (pypdf → Docling)
4. 유사 질문 캐시 threshold(0.95) 정량 튜닝 미수행
5. RBAC / 멀티테넌시 / 민감정보 마스킹 미구현
6. Ollama 어댑터 미구현 — 추상화만 존재
7. Agentic RAG 부재 — 의도적 범위 외

**기술 스택 진화 후보**
- Claude → **Ollama + Qwen2.5-7B**
- BGE-M3 Dense → **+ BM25 Hybrid (RRF) + Reranker**
- ChromaDB → **Qdrant / Milvus**
- pypdf → **Docling**

### 스크립트
> "한계를 정리하면 일곱 가지입니다. 순서는 프로덕트 관점에서 영향도와 투입 대비 효과 기준입니다.
>
> 상위 두 개 — retrieval 분리 평가와 환각 체크 계측 — 은 이미 구현된 평가 하네스 위에서 추가 작업만 하면 되는 항목입니다. **가장 ROI가 높습니다**.
>
> 중간 항목들 — PDF 파서, 캐시 threshold, RBAC/마스킹 — 은 프로덕션 전환 시 반드시 해결해야 하는 기술 부채입니다.
>
> 기술 스택 진화에서 한 가지 강조드리고 싶은 건, **검색 품질 개선의 우선순위** 입니다. 직관적으로는 임베딩 모델을 더 큰 걸로 바꿔야 할 것 같지만, 실제로는 **검색 후단 — BM25를 추가한 Hybrid Search와 cross-encoder Reranker — 가 ROI가 훨씬 높습니다**. 같은 자원으로 Recall이 10~20%p까지 오르기도 합니다. 사내 문서는 '교육비 지원' 같은 고유명사가 많아서 BM25가 dense 검색이 놓치는 정확 매칭을 잡아주기 때문입니다.
>
> Agentic RAG는 앞서 말씀드린 대로 의도적 범위 외이지만, 도입한다면 Query Router부터 단계적으로, LangGraph로 구현하는 게 합리적이라고 봅니다.
>
> 이 모든 개선에서 관통하는 원칙은 **'측정 없이 진행하지 않는다'** 는 것입니다. 그 측정 계획을 다음 슬라이드에서 보여드리겠습니다."

**전달 포인트:**
- 우선순위를 스스로 매길 줄 안다는 건 시니어 자질.
- "임베딩 업그레이드보다 hybrid + reranker가 ROI 높다" — 직관 반대 인사이트.
- 마지막 한 줄로 다음 슬라이드(검증 트랙) 연결.

## 예상 Q&A

### Q1. 왜 Claude를 선택했나요? 외산 모델인데 고객사가 거부하면요?
> "v3 기준으로 Retrieval과 Citation에서 Claude가 97.73%로 Codex의 90.91%를 7%p 앞섰습니다. 외산 의존성은 인지하고 있어서 처음부터 LLMProvider로 추상화했고, Ollama 어댑터는 검증 트랙 03에 정의되어 있습니다. 후보는 Qwen2.5-7B이고, 전환 시 v3 프롬프트의 Few-shot과 JSON 포맷 준수가 유지되는지가 핵심 관찰 포인트입니다."

### Q2. 50개 골든셋이 통계적으로 충분한가요?
> "충분하지 않습니다. PoC 단계의 방향성 판단 근거 정도로 썼습니다. 프로덕션 의사결정에는 도메인별 수백 건 + blind A/B 평가가 필요합니다. 다만 50건이라도 6가지 유형(쉬운/중간/계산/멀티홉/엣지/답변불가)을 균형 있게 배분했고, 이 분포 자체가 평가 설계의 일부입니다."

### Q3. UX 판단이 주관적이지 않나요? Codex가 Latency로 이겼는데요.
> "v3 기준으로 Codex가 우세한 건 Latency뿐이고, Retrieval/Citation/Refusal에서는 Claude가 동률 또는 우세입니다. 즉 UX는 결정타가 아니라 가산점이었습니다. 그리고 Latency는 SSE 스트리밍과 캐시 히트 시 0ms로 체감 지연을 상쇄합니다."

### Q4. BGE-M3의 Sparse를 안 썼는데 왜 굳이 BGE-M3인가요?
> "현재는 Dense만 써서 모델 가치의 일부만 활용 중입니다. 선택 근거는 — 한·영 혼재 성능, 온프렘 가능성, 8K context — 이고, Sparse를 쓰려면 ChromaDB에서 Qdrant로 이전이 선행됩니다. 다음 단계 우선순위는 **DB 이전 → Sparse 활용 (BM25 hybrid + RRF) → Reranker 도입** 순입니다. 검증 트랙 02가 이 작업입니다."

### Q5. Agentic RAG는 왜 안 하셨나요?
> "의도적으로 범위 밖에 두었습니다. Query Router나 Self-correction은 LLM 호출 비용·지연·복잡도를 추가하는데, 측정 없이 도입하면 PoC 신뢰도를 해칩니다. 도입 시점에는 LangGraph로 구현할 계획입니다 — 본질적으로 조건부 분기와 루프가 있는 상태 기계라 직접 짜면 코드 품질이 빠르게 저하되는 영역이기 때문입니다."

### Q6. LangChain은 왜 안 쓰셨나요?
> "현재 파이프라인이 직선이라 LangChain의 추상화 비용이 가치보다 컸습니다. 직접 구현으로 5단계 파이프라인의 명시성과 provider/cache의 세밀한 통제를 확보했습니다. 다만 Agentic RAG로 확장하는 시점에는 LangGraph(LangChain 계열의 그래프 워크플로우 도구) 도입을 검토합니다 — 직선이 아닌 분기/루프 영역에서는 프레임워크의 가치가 명확합니다."

### Q7. ChromaDB를 프로덕션에서 쓸 수 있나요?
> "어렵습니다. RBAC 메타데이터 필터링, BGE-M3 Sparse를 쓰는 Hybrid retrieval, 수백만 벡터 규모 중 어느 하나라도 들어오면 Qdrant나 Milvus로의 이전이 필요합니다. 현재는 Vector DB 접근을 추상화 뒤에 두어 교체 비용을 줄이는 설계까지만 해두었습니다."

### Q8. 환각 이중 체크가 실제로 얼마나 효과적인가요?
> "v3 프롬프트 + 서버 단 매칭의 조합으로 Refusal 100%를 달성한 건 사실입니다. 다만 솔직히 2차 체크의 발동률과 적중률은 아직 측정하지 못했습니다. 즉 '프롬프트만으로 충분한지, 실제로 프롬프트 실패를 구제한 케이스가 얼마나 되는지'를 모릅니다. 이게 한계 슬라이드의 우선순위 2번이고 다음 반복의 핵심 과제입니다."

### Q9. PDF 파서의 한계가 실제 고객사 문서에서 치명적일 텐데요?
> "동의합니다. 사내 문서는 표·다단 비중이 높은데 pypdf가 약합니다. 다만 PDF→마크다운 변환을 추가해 번호 헤더 감지와 구조 보존은 일부 개선했습니다. 검토한 대안은 PyMuPDF + pdfplumber, IBM Docling, LlamaParse — LlamaParse는 온프렘 제약으로 제외, 나머지는 실제 고객사 샘플 문서로 비교 테스트해야 선택 가능합니다."

### Q10. 임베딩 모델을 더 큰 걸로 바꾸면 검색 품질이 더 좋아지지 않을까요?
> "직관적으로는 그렇지만, 실제로는 ROI가 낮은 편입니다. BGE-M3는 한국어 RAG에서 이미 SOTA급이고, 더 큰 모델로 바꿔도 Recall@10이 보통 2~5%p만 오릅니다. 같은 자원으로 더 큰 효과를 보는 건 **검색 후단 — Hybrid Search(BM25+dense+RRF)와 Reranker** 입니다. 사내 문서는 고유명사가 많아서 BM25가 dense가 놓치는 정확 매칭을 잡아주기 때문에 Recall이 10~20%p까지 오르기도 합니다. 검증 트랙 02가 이 가설을 정량 검증하는 작업입니다."

### Q11. Semantic Cache의 threshold 0.95는 어떻게 정했나요?
> "솔직히 경험적 값입니다. '교육비 지원 금액?' / '교육비 한도?' 같은 변형은 잡되, '교육비' / '재택근무' 같은 다른 주제는 구분되는 지점으로 테스트했습니다. 정량적으로 threshold별 hit rate와 false hit를 측정한 건 아닙니다. 0.85/0.9/0.95/0.99 각각의 정밀도·재현율을 구하는 게 다음 단계 과제입니다."

### Q12. 만약 이 PoC를 실제 OfficeAgent처럼 제품화한다면 첫 스프린트에 뭘 하시겠어요?
> "세 가지를 묶겠습니다. 첫째, 검증 트랙 01부터 — gold passage 라벨링과 retrieval 분리 평가로 측정 기반을 확보. 둘째, 실제 고객사 샘플로 PDF 파서 교체 검증 — retrieval 품질의 상한이 결정됩니다. 셋째, RBAC를 vector DB 메타데이터 필터링으로 최소 구현 — 보안 요구는 타협이 어렵습니다. Agentic RAG는 이 세 가지 이후에 Query Router부터 LangGraph로 단계적으로 도입하겠습니다."

- Slide 10 OfficeAgent 비교는 **가장 정성스럽게** 말하기 — Agentic RAG / LangGraph 언급으로 시각의 깊이를 보여줄 수 있는 자리

**라이브 데모 리허설**
- 인터넷 끊김·모델 응답 지연 대비 **녹화본 백업** 필수

- 캐시 히트 시연 (같은 질문 재전송) 포함

**암기할 코드 위치 3개**
