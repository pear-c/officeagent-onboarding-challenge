## 3. 갭 분석 — "이 프로토에서 어느 부분을 디벨롭하면 적용 가능한가"

### 3.1 우선순위 상 (면접/제품 양쪽에서 임팩트 큰 것)

#### 🥇 ① **Agentic RAG로 진화** (가장 중요)
회사가 키워드로 밀고 있는 "Agentic RAG"는 단순 retrieval이 아니라 **질문 의도 분석 → 재정식화 → 멀티스텝 검색 → 자가 검증** 흐름.

**현재 프로젝트 상태**: 단일 `embed → top-5 retrieve → LLM` 파이프라인
**디벨롭 방향**:
- **Query Rewriting**: 사용자 질문을 LLM이 검색 친화적으로 재작성 (예: "연차 얼마?" → "연차 휴가 지원 일수 입사년수별")
- **Query Decomposition**: multi-hop 질문을 subquery로 분해
- **Self-Reflection**: 답변 후 "이 답변이 문서에 정확히 근거 있는가?" 재검증
- **HyDE**: 가상 답변 생성 → 그 답변으로 검색 (짧은 질문의 검색 품질 향상)

**구현 비용**: 중간 — 기존 `rag_service.py`에 전처리/후처리 단계 추가
**적용 위치**: [app/services/rag_service.py](../app/services/rag_service.py) + [app/prompts/templates.py](../app/prompts/templates.py)

#### 🥈 ② **멀티테넌시 (워크스페이스 격리) 설계**
회사는 RBAC + 워크스페이스 격리를 보안의 핵심으로 판매. 내 프로젝트는 단일 유저 가정.

**디벨롭 방향**:
- `tenant_id` 개념 도입
- Chroma: 컬렉션 단위 분리 (`docs_{tenant_id}`)
- Redis: 키 프리픽스 (`cache:exact:{tenant_id}:{hash}`)
- Bearer 토큰 인증 → 요청에서 `tenant_id` 추출
- 문서 업로드/질의 모두 tenant 범위 내에서만 동작

**구현 비용**: 중간 — 핵심은 서비스 계층에 `tenant_id`를 주입하는 것
**적용 위치**: [app/api/routers/](../app/api/), [app/services/](../app/services/), [app/vectorstore/](../app/vectorstore/), [app/cache/](../app/cache/)

#### 🥉 ③ **온프레미스용 로컬 LLM 어댑터**
회사가 온프레미스를 판매 축으로 내걸었는데, Claude/Codex CLI는 온프레미스 부적합.

**디벨롭 방향**:
- `LocalLLMProvider` 추가 (Ollama, vLLM, llama.cpp 연동)
- 기존 `LLMProvider` 인터페이스 그대로 사용 → **코드 변경 없이 어댑터만 추가**
- `.env`로 `LLM_ANSWER_PROVIDER=ollama` 선택

**구현 비용**: 낮음 — 어댑터 패턴 덕분. 90% 설계가 이미 된 상태
**적용 위치**: [app/llm/](../app/llm/) 에 `local_provider.py` 추가

### 3.2 우선순위 중 (인지/설계만 해도 충분)

#### ④ **PII 마스킹 (민감정보 자동 처리)**
회사가 "준비 중" 기능으로 언급. 내 프로젝트에 추가하면 **회사 로드맵에 기여 가능**한 지점.

**디벨롭 방향**:
- 입력 단계: 질문에서 주민번호/전화번호/이메일 정규식 탐지 → 마스킹
- 출력 단계: LLM 답변에서 PII 유출 체크
- 라이브러리: `presidio`(MS 오픈소스) 또는 자체 정규식

**구현 비용**: 낮음 — 미들웨어 추가
**적용 위치**: [app/api/routers/query.py](../app/api/routers/query.py) 전후처리

#### ⑤ **라벨/메타데이터 기반 문서 관리**
현재 파일명만 있음. 회사는 **"라벨 기반 문서 관리"** 를 기능으로 명시.

**디벨롭 방향**:
- 문서 업로드 시 태그(`["HR", "공지", "2026"]`) 받기
- Chroma metadata에 저장
- 질의 시 태그로 필터링 (`where={"tags": {"$in": ["HR"]}}`)
- 부서별 스코프 검색 가능

**구현 비용**: 낮음 — Chroma는 메타데이터 필터 네이티브 지원

#### ⑥ **문서 포맷 확장** (Word, PPT)
회사는 PDF + **Word + PPT + Email** 지원. 내 과제는 PDF/TXT/MD.

**디벨롭 방향**:
- `python-docx`, `python-pptx`, `email` 모듈 추가
- `text_extractor.py`에 포맷 분기 확장
- 동일 청킹 파이프라인 재활용 가능 (마크다운 변환)

**구현 비용**: 낮음

**효과**: 역질문 — 내가 이해하고 준비했음을 보여주면서 대화 열기

> "월 9천원이라는 가격은 LLM 호출 비용 관리가 핵심일 텐데, 제가 설계한 **3단계 캐시(정확 일치 + 유사 질문 + 전체 무효화)** 는 이 관점에서 직접 연결됩니다. 특히 유사 질문 캐시로 cosine 0.95 이상은 LLM 호출을 건너뛰게 설계했고, 동일 질문은 13초 → 0ms로 응답됩니다."

**효과**: 비즈니스 감각 + 기술 연결 — 비용 구조를 이해하고 설계했다는 시그널

### 🎯 메시지 ④ — 온프레미스 대응을 위한 아키텍처
> "과제에서는 Claude/Codex SDK를 썼지만, **`LLMProvider` 인터페이스 + 어댑터 패턴**으로 추상화했습니다. 온프레미스 시나리오에선 이 SDK들이 불가하니까 **Ollama나 vLLM 기반 로컬 모델 어댑터를 추가**하면 되고, 이게 설계 변경 없이 가능합니다. 이 부분이 회사의 온프레미스 배포 축과 직결된다고 봤습니다."

**효과**: 약점("Claude는 온프레미스 안 됨")을 강점(확장 가능한 설계)으로 전환

### 🎯 메시지 ⑤ — 평가 하네스 = 제품 품질 문화
> "제가 8일 중 2일을 **50케이스 평가 하네스 구축**에 썼습니다. 이유는 직감이 아닌 데이터로 기술 선택을 하고 싶었기 때문입니다. 실제로 'Codex가 점수 높다 → UI 비교로 Claude 선택'이라는 의사결정을 이걸로 뒤집었습니다. 제품 팀에 이런 자동화된 평가 시스템이 있으면 프롬프트 튜닝이나 모델 교체 의사결정이 **몇 시간 안에** 가능해집니다."

## 5. 예상 심층 질문 & 준비된 답변

### Q1. "우리 제품은 Agentic RAG를 쓰는데, 본인 과제는 그 수준까지 안 갔잖아요?"

**A.** 맞습니다. 8일 기한 내에서는 기본 RAG의 품질을 높이는 쪽에 우선순위를 뒀습니다. 다만 Agentic RAG로 가는 확장 경로는 설계해뒀습니다:
- (1) Query Rewriting 단계 추가 — `rag_service.py`의 `answer()` 앞에 LLM 한 번 더 호출
- (2) Multi-hop 질문 탐지 → 분해 → 각각 retrieve → 통합
- (3) Self-check 단계 — 답변 후 "근거가 실제 문서에 있는가?" 재검증
특히 (3)은 제가 환각 억제에서 만든 "이중 방어" 개념의 자연스러운 확장입니다. 프롬프트 1차 + 서버 패턴 매칭 2차였던 것이, 프롬프트 1차 + 서버 패턴 2차 + LLM 자가 검증 3차가 되는 거죠.

### Q2. "오픈소스 LLM을 써야 하는데 Claude/Codex 경험만 있지 않나요?"

**A.** SDK 종속을 피하려고 처음부터 `LLMProvider` ABC로 추상화했습니다. Claude Provider와 Codex Provider가 이미 2개의 구현체고, Ollama나 vLLM 기반 Provider를 추가하면 호출 측 코드는 변경 없이 작동합니다. 더 중요한 건 **모델 교체 시 프롬프트 튜닝이 필요한가**를 평가 하네스로 측정할 수 있다는 점인데, 이 인프라가 갖춰져 있으면 새 모델 도입이 2~3일 내 가능합니다.

### Q3. "멀티테넌시를 어떻게 설계할 건가요?"

**A.** 세 층에서 격리해야 합니다:
- **벡터 DB**: Chroma 컬렉션을 `docs_{tenant_id}`로 분리. 컬렉션 간 검색 누수 불가능
- **캐시**: Redis 키 프리픽스 `cache:exact:{tenant_id}:{sha}`. `invalidate_all()`도 tenant 스코프로 변경
- **API**: JWT/세션에서 `tenant_id` 추출 → FastAPI `Depends`로 서비스 계층에 주입
RBAC 추가 시엔 `tenant_id` 위에 `user_id` + `role` + `department` 필터를 메타데이터에 얹어서 벡터 검색 단에서 `where` 절로 걸러내는 구조가 됩니다.

### Q4. "PDF 외에 Word/PPT는 어떻게 지원할 건가요?"

**A.** `text_extractor.py`에 포맷별 분기가 있고, 각 포맷은 최종적으로 **마크다운 문자열**로 통일시킵니다. 그래서:
- `.docx` → `python-docx`로 문단/헤딩 추출 → `#`, `##` 마크다운 변환
- `.pptx` → `python-pptx`로 슬라이드별 텍스트 + 제목 → 슬라이드별 섹션
- `.eml` → `email` 모듈로 헤더(From/Subject/Date) + 본문 → 구조화된 마크다운
이후 청킹 파이프라인(헤더 분할 → 짧은 섹션 병합)은 **재사용** 가능합니다. 이 재사용 가능한 구조를 미리 만들어 둔 게 확장 비용을 낮춥니다.

### Q5. "회사가 언급한 '민감정보 자동 마스킹'을 본인이라면 어떻게 구현할 건가요?"

**A.** 두 지점에서 처리합니다:
- **Ingestion 시점**: 문서 업로드 단계에서 주민번호/전화번호/이메일 정규식 탐지 → 마스킹된 버전을 벡터화 + 원본은 암호화 저장. 검색 결과는 마스킹된 텍스트만 LLM에 전달.
- **Query 응답 시점**: LLM 답변을 반환 직전 PII 탐지 한 번 더 (방어선).
한국어 특화로는 **주민번호(XXXXXX-XXXXXXX), 사업자번호, 계좌번호** 패턴이 중요한데, 오픈소스로는 MS Presidio가 있고 한국어 엔티티는 자체 커스텀 인식기를 추가하는 방식이 현실적입니다. 이게 "학습 배제 원칙"과 결합되면 **LLM에 노출되기 전에 마스킹**이라는 보안 축 하나가 더 생깁니다.

### Q6. "본인 프로젝트를 회사 제품에 넣는다면 어느 코드가 쓸만한가요?"

**A.** 3가지를 바로 꼽을 수 있습니다:
1. **평가 하네스** (`eval/`) — 골든셋 + 7메트릭 + 모델 비교 스크립트. 제품 팀에 이런 도구가 없다면 이식 가치가 매우 큽니다.
2. **프롬프트 v3의 이중 방어 패턴** — Few-shot + 동의어 금지 + 서버 패턴 매칭. Refusal 100% 재현 가능한 설계입니다.
3. **청킹 하이브리드** (포맷별 최적화) — PDF의 번호 섹션을 마크다운 변환해서 `.md` 파이프라인 재활용하는 트릭은 Word/PPT 확장 시 그대로 적용됩니다.
