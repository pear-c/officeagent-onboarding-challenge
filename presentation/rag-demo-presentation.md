>
> **[시나리오 1 실행]** — 첫 번째는 한 문서 안에 답이 있는 표준 케이스입니다. 답변과 함께 근거 청크가 반환되는 것을 확인하실 수 있습니다.
>

### 스크립트
> "첫 번째 의사결정입니다. 과제에서 Claude Code SDK나 Codex CLI 중 택 1하라는 조건이 있었는데, 온프렘 시나리오에서는 둘 다 쓸 수 없다는 점을 고려해 처음부터 LLMProvider 인터페이스로 추상화했습니다.
>
> Claude와 Codex 두 구현체를 50개 골든 데이터셋과 7개 메트릭으로 비교했습니다. 초기 v2 프롬프트에서는 Claude의 Refusal 정확도가 83%에 그쳐 Codex가 우세했는데, Few-shot 예시와 동의어 금지를 추가한 v3 프롬프트를 적용한 후 Claude의 Refusal도 100%에 도달했습니다. v3 기준으로는 Retrieval과 Citation에서 Claude가 97.73%로 Codex의 90.91%를 앞서고, Keyword Hit과 Latency만 Codex 우위입니다.
>
> 즉 속도 외의 거의 모든 영역에서 Claude가 동률 또는 우세했고, 여기에 답변 구조화(번호·불릿·볼드) UX 차이까지 고려해서 Claude를 기본 모델로, Codex를 대안 옵션으로 확정했습니다. 속도 차이는 SSE 스트리밍과 3단계 캐시로 체감 지연을 상쇄합니다.
>
> 다만 이 판단에도 한계가 있습니다. 50건 규모는 통계적 결론을 내기엔 부족하고, 단일 평가자 편향이 남아 있습니다. 프로덕션에서는 도메인별 수백 건 + blind A/B 평가가 필요하다고 봅니다."

**전달 포인트:** v2→v3 튜닝 서사를 함께 풀어내면 "같은 모델도 프롬프트로 바꿀 수 있다"는 깊이가 드러남. Claude 선택 근거를 UX 단일 축이 아니라 *"v3 이후 지표 + UX"* 이중 축으로 방어.

## Slide 6 — 의사결정 2: 임베딩 & 청킹 (2:30)

### 슬라이드 내용
**임베딩: BGE-M3**

| 선택 근거 | 한계 |
|---|---|
| 한·영 혼재 사내 문서에 안정적 | Dense only 사용 — Sparse 미활용 |
| API 과금 없음, 온프렘 가능 | Retrieval 단독 평가 미수행 (자기 검증에서 보완) |
| Dense + Sparse + 8K context 단일 모델 | |

**청킹: 문서 타입별 분기**
- **Markdown** — 헤더 기반 + 상위 헤더 경로 메타데이터 보존
- **PDF** — pypdf + 긴 섹션 2단계 재분할
- **공통** — 섹션이 임계치 초과 시 재귀 분할

### 스크립트
> "임베딩은 BGE-M3를 선택했습니다. 한국어와 영어가 혼재하는 사내 문서 환경에 안정적이고, 오픈소스라 온프렘 배포에 적합합니다. 무엇보다 Dense·Sparse·Long-context를 단일 모델로 지원해 향후 Hybrid retrieval 확장의 기반이 됩니다.
>
> 한계도 명확합니다. 현재는 Dense embedding만 활용하고 있어 모델 가치의 일부만 쓰고 있습니다. 또한 임베딩 자체의 retrieval 성능은 LLM 평가와 분리해서 측정하지 못했습니다. 이 두 가지는 자기 검증 단계에서 일부 보완했고, 뒤에서 결과를 보여드리겠습니다.
>
> 청킹은 문서 구조가 의미 단위를 결정한다고 보고 타입별로 분기했습니다. Markdown은 헤더 기반 분할에 상위 헤더 경로를 메타데이터로 함께 저장했습니다. 이렇게 하면 검색된 청크가 어느 챕터·절에 속하는지의 컨텍스트가 임베딩에 반영됩니다. 긴 섹션은 재귀 분할로 2단계 처리합니다.
>
> PDF는 pypdf로 단순 추출했는데, 이게 현재 가장 큰 한계입니다. 표와 다단 레이아웃 보존이 약해서, 실제 사내 문서처럼 표 비중이 높으면 retrieval 품질이 떨어집니다. LlamaParse도 검토했는데 외부 API라 온프렘에서 제외했습니다. 프로덕션에서는 Docling이나 PyMuPDF + 전용 표 추출 도구로 옮겨야 한다고 봅니다."

**전달 포인트:**
- BGE-M3 선택 근거를 "온프렘 + 확장성"으로 프레이밍 (비용-성능 프레이밍은 약하므로 피함).
- PDF 파서 한계는 숨기지 말고 먼저 인정. "다음 단계" 패키징.

## Slide 7 — 의사결정 3: Vector DB & 3단계 캐시 (1:30)

### 슬라이드 내용

**Vector DB: ChromaDB**

| PoC 근거 | 프로덕션 한계 | 다음 단계 |
|---|---|---|
| Docker 1줄 셋업, 평가 파이프라인 빠른 구동 | RBAC 메타데이터 필터링·Sparse 지원·대규모 운영 약함 | Qdrant / Milvus 이전 |

**Cache: Redis + Chroma 이중 구성 — 3단계 설계**

| 단계 | 구현 | 키 / 방식 | TTL |
|---|---|---|---|
| ① 정확 일치 | Redis | SHA-256(question) → `cache:exact:{hash}` | 1시간 |
| ② 유사 질문 | **Chroma `cache_questions` 컬렉션** | 질문 임베딩 → cosine ≥ 0.95 | 1시간 |
| ③ 무효화 | 문서 업로드 시 전체 QA 캐시 삭제 | 좀비 캐시(TS-008) 방지 | — |

**체감 효과**
- 캐시 miss (RAG 전체 실행): ~13.6초
- 정확 일치 hit: **0ms** (LLM 호출 건너뜀)
- `answerable=false` 응답은 **캐시 미저장** (문서 추가 시 stale 방지)

### 스크립트
> "Vector DB는 ChromaDB를 선택했습니다. Docker 한 줄로 띄워지고, 평가 파이프라인을 빠르게 돌리는 게 1차 목표였기 때문입니다.
>
> 다만 프로덕션 요구사항 중 어느 하나라도 들어오면 교체가 필요하다고 봅니다 — RBAC 기반 메타데이터 필터링, BGE-M3 Sparse 활용 Hybrid retrieval, 수백만 벡터 규모. 이 세 가지가 ChromaDB의 약점이고, Qdrant나 Milvus로의 이전이 현실적입니다.
>
> 캐시는 3단계로 구성했습니다. 1단계는 Redis에 질문 SHA-256 해시를 키로 한 정확 일치 캐시입니다. 2단계가 **Semantic Cache** 인데, 별도 도구를 쓰지 않고 Chroma에 `cache_questions`라는 컬렉션을 하나 더 둬서 질문 임베딩을 저장하고 cosine 유사도 0.95 이상이면 히트로 판정합니다. 같은 의미 다른 표현도 잡아냅니다. 3단계는 문서 업로드 시 전체 QA 캐시를 삭제하는 무효화 로직입니다.
>
> 무효화를 파일별 추적이 아니라 전체 삭제로 선택한 이유는, 빈 의존성을 가진 '좀비 캐시' 엣지 케이스가 발견됐기 때문입니다 — 문서가 없을 때 '찾을 수 없다'고 답한 캐시는 어떤 파일과도 연관이 없어서, 나중에 관련 문서를 업로드해도 무효화되지 않는 문제였습니다. 그래서 `answerable=false` 응답 자체를 캐시에 저장하지 않고, 문서 변경 시엔 전체 무효화하는 단순한 원칙을 택했습니다.
>
> 다음 단계는 유사 질문 캐시의 **threshold 튜닝**입니다. 현재 0.95는 경험적으로 정한 값이고, threshold별 hit rate와 false hit를 측정하는 작업이 필요합니다."

**전달 포인트:**
- Semantic Cache가 **이미 구현된 자산**임을 명확히. 많은 PoC가 놓치는 영역이라 차별화 포인트.
- 전체 무효화 선택 근거는 *"이론적 완벽보다 엣지 케이스 없는 단순함"* 으로 설계 철학을 드러냄.

## Slide 8 — 환각 억제 이중 레이어 (2:00)

### 슬라이드 내용

**Layer 1 — 프롬프트 레벨**

### 스크립트
> "환각 억제는 두 레이어로 구현했습니다.
>

>

**전달 포인트:**

## Slide 9 — OfficeAgent와의 비교 (3:00)

### 슬라이드 내용

| 영역 | OfficeAgent | 본 구현 | 격차 해소 방향 |
|---|---|---|---|
| RAG 방식 | Agentic RAG | Naive + Advanced 요소 일부 | Query 의도 분류부터 단계적 |

>
> RBAC, 민감정보 자동 마스킹, 온프렘 배포 — 이 셋은 OfficeAgent가 프로덕트로 해결한 영역이고, 제 PoC가 다루지 않은 부분입니다. 다만 각 영역에 대한 확장 경로는 설계에 반영했습니다.
>
> RBAC는 vector DB 레벨의 메타데이터 필터링으로 1차 구현이 가능합니다. 마스킹은 현재 정규식 기반 차단 로직의 확장선입니다. 그리고 온프렘 배포는 LLMProvider 추상화 덕에 Claude API 의존성을 Ollama 계열로 교체 가능한 구조입니다.
>
> 정리하면, 제 PoC와 OfficeAgent는 같은 문제 — 환각 억제된 사내 문서 Q&A — 를 푸는데, 저는 파이프라인 정확성에, OfficeAgent는 제품화 전반에 집중한 차이입니다."

**전달 포인트:**

## Slide 10 — 자기 검증: 측정 계획과 진행 중인 실험 (2:00)

| # | 실험 | 측정 지표 | 현재 상태 |

| ① | Retrieval 분리 평가 — gold passage 라벨링 | Recall@K (K=5/10), MRR, nDCG@10 | 🔜 라벨링 중 / 측정 예정 |
| ② | Reranker 도입 효과 — bge-reranker-v2-m3 | Dense only vs Dense+Rerank (Recall·MRR·p95) | 🔜 구현 예정 |

**측정 설계 — 인과 귀속(attribution) 원칙**
- retrieval과 generation을 **분리 측정** → 개선이 어디서 왔는지 구분 가능
- 각 실험에 **지연시간 p50/p95 병기** → 품질·지연 트레이드오프 가시화
- end-to-end 답변 품질(기존 7메트릭)과 **함께 비교** → retrieval 개선이 답변 품질로 이어지는지 검증

### 스크립트
> "과제 완료 후, 면접 준비 과정에서 현재 구현을 한 단계 더 밀어보는 자기 검증 트랙을 열어두고 실행 중입니다. 세 가지 실험을 병렬로 잡았습니다.
>
> 첫째, retrieval 평가를 end-to-end에서 분리하는 작업입니다. 지금까지는 '질문 → 답변' 전체 파이프라인만 지표화했는데, 개선이 어느 단계에서 왔는지 귀속시키려면 50개 질문 각각에 '이 질문에 답하려면 필요한 청크'를 gold passage로 라벨링하고 Recall@K와 MRR을 따로 측정해야 합니다. 지금 라벨링이 진행 중입니다.
>
> 둘째, Reranker 도입입니다. BGE-M3를 골랐으면 자연스럽게 짝이 되는 bge-reranker-v2-m3를 붙여 retrieval 품질을 한 단계 올리는 실험인데, 이게 end-to-end 답변 품질로 연결되는지를 첫 실험의 라벨링을 기반으로 측정할 계획입니다.
>
> 셋째, Ollama 어댑터입니다. `LLMProvider` 추상화 덕분에 구현 자체는 하루 안쪽 작업이지만, 프롬프트는 재튜닝이 필요할 거라고 예상합니다 — Qwen2.5-7B에서 v3 프롬프트의 Few-shot과 JSON 포맷 준수가 얼마나 유지되는지가 핵심 측정 포인트입니다.
>
> 발표 시점까지 완료된 실험 결과는 이 슬라이드에 그대로 반영해서 공유드리고, 완료 안 된 부분은 측정 계획 그대로 공유드릴 예정입니다. PoC 단계에서 'Naive RAG를 했다'로 끝내지 않고, 다음 반복의 측정 가설을 명확히 해두는 것 자체가 검증의 가치라고 보고 있습니다."

**전달 포인트:**
- **허구 수치를 보여주지 않음.** 실측이 있는 실험만 수치 공유, 나머진 설계 그대로.
- "무엇을 모르는지 알고 있고, 어떻게 측정할 건지 안다" 는 메타 능력 어필.
- 발표 당일까지 ①②③ 중 하나라도 수치 나오면 슬라이드 바로 업데이트 가능하도록 구조 유지.

## 예상 Q&A — 답변 준비

### Q1. 왜 Claude를 선택했나요? 외산 모델인데 고객사가 거부하면요?
> "과제에서 Claude SDK나 Codex CLI 중 택 1 조건이 있어서 두 개 다 구현하고 v3 프롬프트 + 50개 골든셋 7메트릭으로 비교했습니다. 속도만 Codex 우세였고 Retrieval·Citation 정확도는 Claude가 97.73%로 앞섰습니다. 외산 모델 의존성은 인지하고 있어서 처음부터 LLMProvider 인터페이스로 추상화했고, Ollama 어댑터는 인터페이스 정합성까지 설계한 상태에서 실제 구현은 면접 준비 중 진행 중입니다. 후보 로컬 모델은 Qwen2.5-7B 또는 Qwen2.5-14B를 생각하고 있습니다 — 한국어 성능이 Llama 계열보다 우세하다는 2026년 현재 컨센서스 때문입니다. 다만 로컬 모델 전환 시 v3 프롬프트의 Few-shot과 JSON 포맷 준수가 얼마나 유지되는지는 제 평가 하네스로 하루 단위 측정-개선 루프가 가능하다는 점이 가장 큰 자산이라고 생각합니다."

### Q2. 50개 골든셋이 통계적으로 충분한가요?
> "충분하지 않습니다. 통계적 결론을 내기에는 부족한 모수이고, PoC 단계의 방향성 판단 근거 정도로 썼습니다. 프로덕션 의사결정에는 도메인별 수백 건 규모의 평가셋과 blind A/B 평가가 필요하다고 봅니다. 이 한계는 제가 발표에서도 먼저 언급드린 이유이기도 합니다."

### Q3. UX 판단이 주관적이지 않나요? Codex가 수치로 이겼는데요.
> "중요한 건 v2 프롬프트 시점과 v3 시점이 다르다는 점입니다. v2에서는 Claude Refusal이 83%라 Codex가 환각 억제에서 우세했지만, v3에서 Few-shot과 동의어 금지를 추가한 후 Claude도 100%에 도달했습니다. v3 기준으로는 Retrieval과 Citation에서 Claude가 97.73%로 Codex의 90.91%를 앞서고, Keyword Hit과 Latency만 Codex 우세입니다. 즉 UX 차이가 결정타였다기보다, v3 이후 대부분의 지표에서 Claude가 동률 또는 우세한 상태에서 답변 구조화 UX가 추가 가산점이 된 상황입니다. 다만 50건 + 단일 평가자라는 모수 한계는 분명합니다. 수백 건 blind 평가로 확장하면 결론이 바뀔 가능성을 인정합니다."

### Q4. BGE-M3의 Sparse를 안 썼는데 왜 굳이 BGE-M3인가요?
> "날카로운 지적이십니다. 현재는 Dense만 써서 모델 가치의 일부만 활용하고 있습니다. 선택 근거 자체는 — 한·영 혼재 문서 성능, 온프렘 가능성, 8192 토큰 긴 컨텍스트 — 이지만, 모델을 완전히 활용하려면 Hybrid retrieval로의 확장과 Reranker 도입이 필요합니다. 이 두 가지가 자기 검증 트랙의 ①②번 실험이고, Dense+Sparse Hybrid는 Chroma의 sparse 지원 한계로 Qdrant나 Weaviate로의 이전이 선행되어야 하는 작업이라 우선순위는 Reranker 다음에 두었습니다."

### Q5. Agentic RAG는 왜 안 하셨나요?
> "의도적으로 범위 밖에 두었습니다. Agentic RAG는 Query Router나 Self-correction처럼 LLM이 흐름을 결정하는 지점이 추가되는데, 각각이 호출 비용·지연·복잡도를 올립니다. 이게 실제 품질 개선으로 이어지는지를 측정 없이 도입하면 오히려 PoC의 신뢰도를 해친다고 봤습니다. 다음 단계로는 Query 의도 분류부터 단계적으로 도입하면서 각 단계의 효용을 측정할 계획입니다."

### Q6. ChromaDB를 프로덕션에서 쓸 수 있나요?
> "제 판단으로는 어렵습니다. PoC 속도를 우선해서 골랐고, 프로덕션 요구사항 — RBAC 기반 메타데이터 필터링, BGE-M3 Sparse를 쓰는 Hybrid retrieval, 수백만 벡터 규모 — 중 어느 하나라도 들어오면 Qdrant나 Milvus로의 이전이 필요합니다. 현재는 Vector DB 접근을 추상화 레이어 뒤에 두어 교체 비용을 줄이는 설계 정도까지만 해두었습니다."

### Q7. 환각 이중 체크가 실제로 얼마나 효과적인가요?
> "솔직히 말씀드리면, 2차 체크의 발동률과 적중률은 아직 정량 측정하지 못했습니다. 이게 제가 꼽는 현재 구현의 최상위 약점입니다. 체크가 너무 느슨하면 무의미하고 너무 공격적이면 정상 답변까지 거르기 때문에, false positive·false negative를 분리 측정해야 하는데 이건 다음 반복의 우선과제로 두었습니다."

### Q8. PDF 파서의 한계가 실제 고객사 문서에서 치명적일 텐데요?
> "동의합니다. 사내 문서는 표와 다단 레이아웃 비중이 높은데, pypdf가 이 부분에 약합니다. 검토한 대안은 세 갈래입니다 — PyMuPDF + camelot/pdfplumber 조합, IBM Docling, 그리고 LlamaParse. LlamaParse는 온프렘 제약으로 제외되고, 남는 건 PyMuPDF 조합과 Docling인데, 이건 실제 고객사 문서 샘플로 테스트해봐야 선택할 수 있다고 봅니다. PoC 범위에서는 pypdf로 두고, 파서 교체를 첫 프로덕션 이터레이션의 과제로 인식하고 있습니다."

### Q9. Retrieval 평가와 end-to-end 답변 품질의 상관관계는 어떻게 측정하실 계획인가요?
> "자기 검증 트랙에서 측정하려는 게 정확히 이 관계입니다. Gold passage 라벨링으로 retrieval 단독 지표(Recall@K, MRR)를 구하고, 같은 50개 질문의 end-to-end 답변 품질(기존 7메트릭)을 함께 보면서 retrieval 개선이 실제 답변 품질 개선으로 이어졌는지 귀속(attribution)을 보는 설계입니다. 예상되는 결과 패턴 두 가지가 있는데 — 첫째, Recall 상승이 답변 품질 상승으로 연결되는 경우. 둘째, Recall은 올랐는데 답변 품질이 정체되는 경우. 후자가 나오면 LLM이 이미 Top-10 노이즈를 처리하고 있었다는 뜻이고, 청크 순서·크기 같은 다른 축으로 최적화 방향을 바꿔야 합니다. 이 분리 자체가 이번 자기 검증의 목적입니다."

### Q10. 만약 이 PoC를 실제 OfficeAgent처럼 제품화한다면 첫 스프린트에 뭘 하시겠어요?
> "세 가지를 묶겠습니다. 첫째, 실제 고객사 샘플 문서로 PDF 파서 교체 검증 — 이게 retrieval 품질의 상한을 결정합니다. pypdf의 표·다단 레이아웃 한계를 Docling이나 PyMuPDF로 해결해야 합니다. 둘째, RBAC를 vector DB 메타데이터 필터링으로 최소 구현 — 보안 요구는 타협이 어렵고, Redis 키 프리픽스와 Chroma 컬렉션 분리를 tenant_id 기반으로 확장하는 설계까지는 미리 해두었습니다. 셋째, 환각 2차 체크의 계측 파이프라인 구축 — 이미 있는 거절 패턴 매칭 로직에 발동률·적중률 로깅을 추가하면 되는 작업입니다. Agentic RAG 요소는 이 셋 이후에 Query Router부터 단계적으로, 각 단계의 효용을 측정해가며 도입하겠습니다. 이미 구현된 Semantic Cache는 threshold 튜닝으로 완성도를 올리는 것이 우선입니다."
