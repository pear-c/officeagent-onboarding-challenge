## Slide 4 — 라이브 데모 (5:00)

### 슬라이드 내용
**시나리오 3종**
1. **단일 문서 질의** — 한 문서에 답이 있는 표준 케이스

화면 옆에 **검색된 청크 / 최종 답변 / citation / 캐시 히트 여부** 를 동시 노출

### 스크립트
> "실제 동작을 보여드리겠습니다. 의도적으로 세 가지 성격의 질문을 준비했습니다.
>
> **[시나리오 1 실행]** — 첫 번째는 한 문서 안에 답이 있는 표준 케이스입니다. 답변과 함께 근거 청크가 반환되는 것을 확인하실 수 있습니다.
>
> **[시나리오 2 실행]** — 두 번째는 두 개 이상의 문서를 종합해야 하는 질문입니다. 여러 청크가 검색되고, LLM이 이들을 종합해 답하는 과정을 보시겠습니다.
>
> **[시나리오 3 실행]** — 세 번째는 업로드 문서에 답이 없는 질문입니다. 시스템이 억지 답을 만들지 않고 '문서에서 근거를 찾을 수 없다'고 응답하는지를 보여드리기 위한 케이스입니다. v3 프롬프트 튜닝 후 이 Refusal 정확도가 100%에 도달했고, 이것이 실제 환각 억제의 가장 중요한 지표라고 봅니다.
>
> 참고로, 같은 질문을 한 번 더 보내면 캐시가 히트되어 0ms에 응답이 돌아옵니다."

- citation이 화면에 보이는지 미리 체크.

## Slide 5 — 의사결정 1: LLM Provider & 평가 (3:00)

### 슬라이드 내용
**LLMProvider 인터페이스** (`app/llm/provider.py`)
```python
class LLMProvider(ABC):
    @abstractmethod
    async def generate(self, system_prompt, user_prompt, ...) -> LLMResponse: ...
    @abstractmethod
    async def stream(self, system_prompt, user_prompt, ...) -> AsyncIterator: ...
```

**구현체 — 현재 2개**
- `ClaudeProvider` ✅ — Claude Code SDK, JSON schema 모드, claude-sonnet-4-6
- `CodexProvider` ✅ — Codex CLI subprocess, JSONL 파싱, 60초 타임아웃

**50개 골든셋 × 7메트릭 평가 결과 — v2 vs v3 비교**

| 메트릭 | Claude v2 | **Claude v3** | Codex | 변화 |
|---|---|---|---|---|
| Retrieval Hit Rate | 93.18% | **97.73%** | 90.91% | +4.55%p |
| Citation Accuracy | 93.18% | **97.73%** | 90.91% | +4.55%p |
| Refusal Accuracy | 83.33% | **100.00%** | 100.00% | **+16.67%p** |
| Keyword Hit Rate | 90.91% | 88.64% | **90.91%** | -2.27%p |
| JSON Parse Rate | 100.00% | 100.00% | 100.00% | — |
| Latency p50 | 10,773ms | 8,803ms | **4,516ms** | -18% |
| Latency p95 | 16,892ms | 15,731ms | **10,557ms** | -7% |

**선택: Claude (v3 이후 지표 + UX 이중 근거)**

### 스크립트
> "첫 번째 의사결정입니다. 과제에서 Claude Code SDK나 Codex CLI 중 택 1하라는 조건이 있었는데, 온프렘 시나리오에서는 둘 다 쓸 수 없다는 점을 고려해 처음부터 LLMProvider 인터페이스로 추상화했습니다.
>
> Claude와 Codex 두 구현체를 50개 골든 데이터셋과 7개 메트릭으로 비교했습니다. 여기서 중요한 건 **v2와 v3 시점의 차이**입니다.
>
> 초기 v2 프롬프트에서는 Claude의 Refusal 정확도가 83%에 그쳤습니다. '문서에 없으면 모른다고 답하라'는 지시를 Claude가 종종 무시하고 억지 답을 생성했습니다. 이 시점에서는 Codex가 환각 억제에서 우세했습니다.
>
> 그래서 프롬프트 튜닝에 집중했습니다. v3에서 세 가지를 변경했습니다 — Few-shot 예시 2개 추가, '확인할 수 없습니다' 같은 동의어 사용 금지, 서버 단 10종 거절 패턴 매칭. 이 이후 Claude의 Refusal이 100%에 도달했고, Retrieval과 Citation에서도 97.73%로 Codex의 90.91%를 7%p 앞섰습니다.
>
> v3 기준으로 Codex가 우세한 건 Keyword Hit Rate와 Latency뿐입니다. 속도 차이는 SSE 스트리밍과 3단계 캐시(히트 시 0ms)로 체감 지연을 상쇄하고, 답변 구조화 UX(번호·불릿·볼드)까지 고려해서 Claude를 기본 모델로 확정했습니다.
>
> 다만 50건 + 단일 평가자라는 모수 한계는 분명합니다. 프로덕션에서는 도메인별 수백 건 + blind A/B 평가가 필요합니다."

**전달 포인트:**
- **v2→v3 튜닝 서사가 이 슬라이드의 심장.** "같은 모델도 프롬프트로 바꿀 수 있다" + "데이터로 의사결정한다"는 두 메시지.
- Claude 선택 근거가 "UX만"이 아니라 **"v3 이후 지표 우세 + UX"** 이중 축.

## Slide 6 — 의사결정 2: 임베딩 & 청킹 (2:30)

### 슬라이드 내용
**임베딩: BGE-M3**

| 선택 근거 | 한계 |
|---|---|
| 한·영 혼재 사내 문서에 안정적 (MTEB Korean Retrieval 상위) | Dense only 사용 — Sparse 미활용 |
| API 과금 없음, 온프렘 가능 | Retrieval 단독 평가 미수행 |
| Dense + Sparse + 8192 토큰 context 단일 모델 | ChromaDB가 Sparse 미지원 → Hybrid 전환 시 DB 이전 필요 |

**청킹: 문서 타입별 분기** (`app/chunking/router.py`)
- **Markdown** — 헤더 기반 분할 + **상위 헤더 경로** 메타데이터 보존 (`"정책 안내 > 교육비 지원"`)
- **PDF** — pypdf 추출 → 번호 헤더 감지 → 마크다운 변환 후 동일 파이프라인 적용 (TS-006)
- **공통** — 섹션이 400자 초과 시 재귀 분할 (overlap 80자)

### 스크립트
> "임베딩은 BGE-M3를 선택했습니다. 한국어와 영어가 혼재하는 사내 문서 환경에 안정적이고, 오픈소스라 온프렘 배포에 적합합니다. 무엇보다 Dense·Sparse·Long-context를 단일 모델로 지원해 향후 Hybrid retrieval 확장의 기반이 됩니다.
>
> 한계도 명확합니다. 현재는 Dense embedding만 활용하고 있어 모델 가치의 일부만 쓰고 있습니다. Sparse를 활용한 Hybrid 검색으로 가려면 ChromaDB가 Sparse를 지원하지 않아 Qdrant 등으로 DB 이전이 선행되어야 합니다.
>
> 청킹은 문서 구조가 의미 단위를 결정한다고 보고 타입별로 분기했습니다. Markdown은 헤더 기반 분할에 상위 헤더 경로를 메타데이터로 함께 저장합니다 — 예를 들어 '교육비 연 100만원'이라는 청크에 '정책 안내 > 교육비 지원'이라는 경로가 붙어서, 검색 시 어느 맥락의 100만원인지 구분이 됩니다.
>
> PDF 처리에서 주목할 점은, pypdf로 텍스트 추출 후 번호 헤더를 감지해 마크다운으로 변환하는 단계를 추가했다는 것입니다. 41페이지짜리 공공데이터 가이드 PDF로 비교했을 때, 동일한 청크 수에서 섹션 메타데이터가 빈 문자열 → 실제 헤더 경로로 바뀌었고 속도도 22% 개선됐습니다.
>
> 가장 큰 한계는 pypdf의 표·다단 레이아웃 보존이 약하다는 점입니다. 프로덕션에서는 Docling이나 PyMuPDF로의 이전이 필요합니다."

**전달 포인트:**
- BGE-M3 선택 근거를 "온프렘 + 확장성"으로 프레이밍.
- 상위 헤더 경로 보존이 **이미 구현된 Advanced 요소**임을 자연스럽게 드러냄.
- PDF 파서 한계는 숨기지 말고 먼저 인정.

## Slide 7 — 의사결정 3: Vector DB & 3단계 캐시 (2:00)

### 슬라이드 내용

**Vector DB: ChromaDB**

| PoC 근거 | 프로덕션 한계 | 다음 단계 |
|---|---|---|
| Docker 1줄 셋업, 50~500 벡터 규모에서 <1ms | RBAC 메타데이터 필터링·Sparse 지원·대규모 운영 약함 | Qdrant / Milvus 이전 |

**Cache: Redis + Chroma 이중 구성 — 3단계 캐시 (모두 구현 완료)**

| 단계 | 구현체 | 키 / 방식 | TTL | 코드 위치 |
|---|---|---|---|---|
| ① 정확 일치 | Redis | SHA-256(question) → `cache:exact:{hash}` | 1시간 | `redis_cache.py` |
| ② **유사 질문 (Semantic Cache)** | **Chroma `cache_questions` 컬렉션** | 질문 임베딩 → **cosine ≥ 0.95** | 1시간 | `cache_service.py:68 get_similar()` |
| ③ 무효화 | 문서 업로드 시 전체 QA 캐시 삭제 | 좀비 캐시(TS-008) 방지 | — | `cache_service.py` |

**실측 체감 효과**
- 캐시 miss (RAG 전체 실행): **~13.6초**
- 정확 일치 / 유사 질문 hit: **0ms** (LLM 호출 건너뜀)
- `answerable=false` 응답은 **캐시에 저장하지 않음** → 문서 추가 후 재질문 시 stale 방지

### 스크립트
> "Vector DB는 ChromaDB를 선택했습니다. Docker 한 줄로 띄워지고, 현재 규모에서 <1ms 성능을 보여줍니다.
>
> 프로덕션 한계는 명확합니다 — RBAC 메타데이터 필터링, Sparse 지원, 대규모 벡터 운영 모두 약합니다. Qdrant나 Milvus로의 이전이 현실적인 다음 단계입니다.
>
> 이 슬라이드에서 핵심은 캐시 설계입니다. 3단계 모두 이미 구현되어 동작하고 있습니다.
>
> 1단계는 Redis에 질문 SHA-256 해시를 키로 한 정확 일치 캐시입니다. 2단계가 핵심인데, **Semantic Cache**입니다. 별도 도구를 쓰지 않고 Chroma에 `cache_questions`라는 컬렉션을 하나 더 둬서 질문 임베딩을 저장하고, cosine 유사도 0.95 이상이면 히트로 판정합니다. '교육비 지원 금액이 얼마인가요?'와 '교육비 한도가 얼마죠?'를 같은 질문으로 인식합니다.
>
> 3단계는 무효화입니다. 문서 업로드 시 전체 QA 캐시를 삭제합니다. 파일별 추적이 아닌 전체 삭제를 택한 이유는 '좀비 캐시' 엣지 케이스 때문입니다 — 문서가 없을 때 '찾을 수 없다'고 답한 캐시는 어떤 파일과도 연관이 없어서, 나중에 관련 문서를 업로드해도 무효화되지 않는 문제입니다. 그래서 `answerable=false` 응답 자체를 캐시에 저장하지 않고, 문서 변경 시엔 전체 무효화하는 단순한 원칙을 택했습니다.
>
> 다음 단계는 threshold 0.95의 정량 튜닝입니다. 현재는 경험적으로 정한 값이고, threshold별 hit rate와 false hit를 측정하는 작업이 남아 있습니다."

**전달 포인트:**
- **Semantic Cache가 이미 구현된 핵심 자산.** 많은 PoC가 정확 일치만 구현하는데, 유사 질문까지 잡아내는 2단계가 차별화.
- 좀비 캐시 → `answerable=false` 미저장 → 전체 무효화의 **설계 사고 과정**을 보여줌.
- threshold 0.95 한계를 먼저 인정.

## Slide 8 — 환각 억제 이중 레이어 (2:00)

### 슬라이드 내용

**Layer 1 — 프롬프트 레벨**
- 문서 근거 없으면 정확히 「제공된 문서에서 해당 내용을 찾을 수 없습니다」로 응답 강제

- JSON 파싱 실패 시 fallback 처리
- `answerable=false` 응답은 출처 반환 차단 + 캐시 미저장

**프롬프트 v1 → v2 → v3 튜닝 히스토리**
| 버전 | 변경 | 문제 해결 | Refusal Accuracy |
|---|---|---|---|
| v1 | JSON 출력 지시 | — | 스트리밍 버그로 미측정 (TS-004) |
| v2 | 스트리밍 전용 프롬프트 분리 | SSE에서 raw JSON 출력 해결 | 83.33% |
| **v3** | Few-shot 2개 + 동의어 금지 + 서버 단 10종 패턴 | LLM 동의어 우회 차단 (TS-009) | **100.00%** |

>
> 2차는 서버 단 검증입니다. LLM이 지시를 완벽하게 따르지 않을 때를 대비해, 10가지 거절 패턴을 코드 레벨에서 한 번 더 매칭합니다. 실제로 프롬프트에 '확인할 수 없습니다' 같은 동의어 금지를 명시했는데도 Claude가 종종 그 표현을 쓰는 경우가 있었습니다. 서버가 그걸 거절로 인식 못하면 `answerable=true`로 오판정되고 근거 없는 답변이 출처까지 표시되는 문제가 있었습니다.
>

>
> 현재 구현의 가장 큰 빈 칸은 서버 단 체크의 발동률·적중률 계측입니다. 너무 느슨하면 무의미하고 공격적이면 정상 답변까지 거르는데, 이걸 false positive·false negative로 분리 측정하는 건 다음 반복의 우선과제입니다."

**전달 포인트:**
- **v2→v3 튜닝 서사가 본 슬라이드의 심장.** "프롬프트를 정말로 공들였다"는 증거.
- 발동률·적중률 미측정은 먼저 인정. "안 했다"가 아니라 "아직 못 했다, 우선과제다".

## Slide 9 — 이미 구현된 Advanced 요소 (1:30)

### 슬라이드 내용

**"Naive RAG가 아닌 이유" — 이미 구현된 Advanced 4가지**

### 스크립트

>
> Ollama 어댑터는 LLMProvider 추상화 덕에 구현 비용은 낮지만, 실제 모델 측정까지 포함하면 하루 이상의 작업입니다. Agentic RAG는 앞서 말씀드린 대로 의도적 범위 외입니다.
>
> 이 모든 개선에서 관통하는 원칙은 '측정 없이 진행하지 않는다'는 것입니다. RAG는 측정하지 않으면 감이 됩니다. 각 컴포넌트의 효용을 정량화할 수 있는 평가 체계가 먼저이고, 그 위에서 개선이 이뤄져야 한다는 것이 지금 시점의 제 결론입니다."

**전달 포인트:** 우선순위를 스스로 매길 줄 안다는 건 시니어 자질. "측정 없이 진행하지 않는다"가 전체 발표를 묶는 테제.

## 예상 Q&A — 답변 준비

### Q1. 왜 Claude를 선택했나요? 외산 모델인데 고객사가 거부하면요?
> "과제에서 Claude SDK나 Codex CLI 중 택 1 조건이 있어서 두 개 다 구현하고 v3 프롬프트 + 50개 골든셋 7메트릭으로 비교했습니다. v3 기준으로 속도만 Codex 우세였고 Retrieval·Citation 정확도는 Claude가 97.73%로 7%p 앞섰습니다. 외산 모델 의존성은 인지하고 있어서 처음부터 LLMProvider 인터페이스로 추상화했습니다. Ollama 어댑터는 아직 구현하지 못했지만, 인터페이스 구조상 `generate()`와 `stream()` 두 메서드만 구현하면 호출 측 코드 변경 없이 연결됩니다. 후보 로컬 모델은 Qwen2.5-7B 또는 14B를 생각하고 있고, 전환 시 v3 프롬프트의 Few-shot과 JSON 포맷 준수가 유지되는지가 핵심 측정 포인트입니다."

### Q2. 50개 골든셋이 통계적으로 충분한가요?
> "충분하지 않습니다. 통계적 결론을 내기에는 부족한 모수이고, PoC 단계의 방향성 판단 근거 정도로 썼습니다. 프로덕션 의사결정에는 도메인별 수백 건 규모의 평가셋과 blind A/B 평가가 필요하다고 봅니다. 다만 50건이라도 6가지 유형(쉬운 질문, 중간, 계산, 멀티홉, 엣지케이스, 답변 불가)을 균형 있게 배분하려 했고, 이 분포 자체가 평가 설계의 일부라고 봅니다."

### Q3. UX 판단이 주관적이지 않나요? Codex가 수치로 이겼는데요.
> "중요한 건 v2 프롬프트 시점과 v3 시점이 다르다는 점입니다. v2에서는 Claude Refusal이 83%라 Codex가 환각 억제에서 우세했지만, v3에서 Few-shot과 동의어 금지를 추가한 후 Claude도 100%에 도달했습니다. v3 기준으로는 Retrieval과 Citation에서 Claude가 97.73%로 Codex의 90.91%를 앞서고, Keyword Hit과 Latency만 Codex 우세입니다. 즉 UX 차이가 결정타였다기보다, v3 이후 대부분의 지표에서 Claude가 동률 또는 우세한 상태에서 답변 구조화 UX가 추가 가산점이 된 상황입니다. 다만 50건 + 단일 평가자라는 모수 한계는 분명합니다."

### Q4. BGE-M3의 Sparse를 안 썼는데 왜 굳이 BGE-M3인가요?
> "날카로운 지적이십니다. 현재는 Dense만 써서 모델 가치의 일부만 활용하고 있습니다. 선택 근거 자체는 — 한·영 혼재 문서 성능, 온프렘 가능성, 8192 토큰 긴 컨텍스트 — 이고, Sparse를 쓰려면 ChromaDB에서 Qdrant 같은 Sparse 지원 DB로 이전이 선행되어야 합니다. 그래서 현재 다음 단계 우선순위는 DB 이전 → Sparse 활용 → Reranker 도입 순으로 잡고 있습니다."

### Q5. Agentic RAG는 왜 안 하셨나요?
> "의도적으로 범위 밖에 두었습니다. Agentic RAG는 Query Router나 Self-correction처럼 LLM이 흐름을 결정하는 지점이 추가되는데, 각각이 호출 비용·지연·복잡도를 올립니다. 이게 실제 품질 개선으로 이어지는지를 측정 없이 도입하면 오히려 PoC의 신뢰도를 해친다고 봤습니다. 다음 단계로는 Query 의도 분류부터 단계적으로 도입하면서 각 단계의 효용을 측정할 계획입니다."

### Q6. ChromaDB를 프로덕션에서 쓸 수 있나요?
> "제 판단으로는 어렵습니다. PoC 속도를 우선해서 골랐고, 프로덕션 요구사항 — RBAC 기반 메타데이터 필터링, BGE-M3 Sparse를 쓰는 Hybrid retrieval, 수백만 벡터 규모 — 중 어느 하나라도 들어오면 Qdrant나 Milvus로의 이전이 필요합니다. 현재는 Vector DB 접근을 추상화 레이어 뒤에 두어 교체 비용을 줄이는 설계까지만 해두었습니다."

### Q7. 환각 이중 체크가 실제로 얼마나 효과적인가요?
> "v3 프롬프트 + 서버 단 매칭의 조합으로 Refusal Accuracy가 100%에 도달한 건 사실입니다. 다만 솔직히 말씀드리면, 2차 체크의 발동률과 적중률은 아직 정량 측정하지 못했습니다. 즉 '프롬프트만으로 충분한데 서버 체크가 안전장치일 뿐인지, 실제로 프롬프트 실패를 구제한 케이스가 얼마나 되는지'를 모릅니다. 이게 현재 구현의 최상위 약점이고 다음 반복의 우선과제입니다."

### Q8. PDF 파서의 한계가 실제 고객사 문서에서 치명적일 텐데요?
> "동의합니다. 사내 문서는 표와 다단 레이아웃 비중이 높은데, pypdf가 이 부분에 약합니다. 다만 PDF→마크다운 변환 단계를 추가해서, 번호 헤더 감지와 구조 보존은 일부 개선했습니다. 검토한 대안은 PyMuPDF + pdfplumber 조합, IBM Docling, LlamaParse 세 갈래인데, LlamaParse는 온프렘 제약으로 제외됩니다. 남는 건 실제 고객사 문서 샘플로 비교 테스트해봐야 선택할 수 있다고 봅니다."

### Q9. Semantic Cache의 threshold 0.95는 어떻게 정했나요?
> "솔직히 경험적 값입니다. 너무 낮으면 다른 의미의 질문이 false hit되고, 너무 높으면 같은 의미 다른 표현을 놓칩니다. 0.95는 '교육비 지원 금액은?' / '교육비 한도가 얼마죠?' 같은 변형은 잡되, '교육비' / '재택근무' 같은 완전히 다른 주제는 구분되는 지점으로 테스트했습니다. 다만 정량적으로 threshold별 hit rate와 false hit rate를 측정한 건 아닙니다. 0.85/0.9/0.95/0.99 각각의 정밀도·재현율을 구하는 게 다음 단계 과제입니다."

### Q10. 만약 이 PoC를 실제 OfficeAgent처럼 제품화한다면 첫 스프린트에 뭘 하시겠어요?
> "세 가지를 묶겠습니다. 첫째, 실제 고객사 샘플 문서로 PDF 파서 교체 검증 — 이게 retrieval 품질의 상한을 결정합니다. 둘째, RBAC를 vector DB 메타데이터 필터링으로 최소 구현 — 보안 요구는 타협이 어렵습니다. 셋째, 환각 2차 체크의 계측 파이프라인 구축 — 이미 있는 거절 패턴 매칭 로직에 발동률·적중률 로깅만 추가하면 됩니다. Agentic RAG 요소는 이 셋 이후에 Query Router부터 단계적으로, 각 단계의 효용을 측정해가며 도입하겠습니다."
