# Lesson & Learned — 면접 발표용 스토리 스크립트

> 이 문서는 면접 발표에서 **직접 말할 스크립트**로 쓰도록 작성됨.
> 스토리 구조: `한 줄 훅 → 가설 → 실패 → 조정 → 결과 → 교훈 → 예상 질문`
> 각 스토리는 60~90초 분량. 총 3개 = 약 4분.

---

## 스토리 ① — "LLM 지시는 100% 지켜지지 않는다. 이중 방어가 필요했다"

### 🎯 한 줄 훅
> "'정확히 이 문구로 답해' 라고 써놨는데, Claude는 동의어를 썼습니다."

### 📐 스토리 (60~90초)

**[가설 — 10초]**
환각 억제의 핵심은 "문서에 없으면 거절한다"입니다.
그래서 프롬프트에 이렇게 썼습니다 —
> "답이 없으면 정확히 **'제공된 문서에서 해당 내용을 찾을 수 없습니다'** 로 답하세요."
서버는 이 문구를 감지해서 `answerable=false`로 판정하는 구조였습니다.

**[실패 — 20초]**
그런데 평가 하네스로 50케이스를 돌려보니 Refusal 정확도가 **83.33%**.
unanswerable 6개 중 1개에서 Claude가 뭐라고 답했냐면 —
> "해당 내용은 **확인할 수 없습니다**"

동의어를 쓴 겁니다. 프롬프트에 "이 문구로 답해"라고 써도, LLM은 helpfulness 성향 때문에 표현을 자연스럽게 바꿔버리는 경향이 있었습니다.
서버는 이걸 거절로 인식 못하고 `answerable=true` 오판정 → 근거 없는 답변이 캐시에 저장되고 출처까지 표시되는 상황이 발생했습니다.

**[조정 — 20초]**
두 가지 방어선을 겹쳤습니다.
- **1차 (프롬프트)**: "동의어 사용 금지" 명시 + Few-shot 예시 2개 (답변 가능/불가 각 1개)
- **2차 (서버)**: 거절 패턴 리스트 매칭
  ```python
  _REFUSAL_PATTERNS = ("찾을 수 없습니다", "확인할 수 없",
                        "답변할 수 없", "정보가 없", ...)
  ```

**[결과 — 10초]**
Refusal **83% → 100%**, Retrieval Hit Rate도 93% → **97.73%**까지 같이 올라갔습니다.

### 💡 일반화 가능한 교훈
- **LLM 프롬프트 지시는 확률적 제어다.** 100% 결정론을 기대하면 실패한다.
- **형식이 중요한 판정(거절 여부, JSON 구조)은 프롬프트 + 서버 검증 이중화가 안전하다.**
- 프롬프트는 1차 방어선, 코드는 2차 방어선.

### 🎤 슬라이드 구성 (2장)

**슬라이드 A: "프롬프트만으로는 부족했다"**
- 제목: LLM 지시는 100% 지켜지지 않는다
- 좌측: 프롬프트 지시 원문 (강조)
- 우측: 실제 Claude 응답 ("확인할 수 없습니다") + ❌ 오판정 흐름도

**슬라이드 B: "이중 방어로 100% 달성"**
- 상단: 프롬프트 측 (Few-shot + 동의어 금지)
- 하단: 서버 측 (_REFUSAL_PATTERNS 코드 스니펫)
- 우상단 숫자 카드: `83% → 100%` (크게)

### ❓ 예상 질문 & 답변

**Q1. "패턴 리스트가 많아지면 유지보수 어렵지 않나요?"**
A. 네, 현재는 하드코딩인데 운영 데이터가 쌓이면 LLM 자체에게 "이 답변이 거절인가?" 판정을 맡기는 self-check 방식으로 진화할 수 있습니다. 단, 비용/지연 트레이드오프가 생기므로 현재 규모에서는 패턴 매칭이 합리적이었습니다.

**Q2. "거절 패턴이 정답 답변에 오탐될 수도 있지 않나요?"**
A. 예를 들어 문서에 "정보가 없다"가 포함된 경우를 상상할 수 있습니다. 현재 전체 답변에서 패턴을 찾는 방식이라 문서 내용을 인용하면 오탐 가능성이 있습니다. 개선안은 (a) 답변의 주절만 검사, (b) LLM에 판정 맡기기, (c) JSON 응답의 `answerable` 필드를 1차 신뢰하고 서버는 최종 검증만 — 실제로 JSON 경로는 (c)를 쓰고 있고 스트리밍만 패턴 매칭을 사용합니다.

**Q3. "왜 Few-shot 예시가 효과가 있었다고 보시나요?"**
A. 프롬프트 지시문은 추상적이지만, Few-shot은 구체적인 입력→출력 패턴을 보여줍니다. Claude는 지시문보다 예시의 패턴을 더 잘 따르는 경향이 있었고, 실측으로 Refusal 16.67%p 상승을 확인했습니다.

## 스토리 ② — "캐시 무효화는 '키 의존성'을 먼저 설계해야 한다"

### 🎯 한 줄 훅
> "거절 답변이 캐시에 박혀서, 문서를 올려도 여전히 '찾을 수 없다' 라고 답하는 좀비 캐시가 생겼습니다."

### 📐 스토리 (60~90초)

**[가설 — 15초]**
캐시 무효화 요구사항은 "문서가 변경되면 관련 캐시 삭제"였습니다.
처음엔 합리적으로 설계했습니다 —
캐시 엔트리에 `source_files=["company-policy.txt"]` 같은 의존성을 저장하고,
해당 파일이 변경되면 그 파일과 연관된 캐시만 삭제.

**[실패 — 25초]**
이런 시나리오가 생겼습니다 —
1. 문서 업로드 **전에** 질문 → "찾을 수 없습니다" (당연함, 문서 없으니까)
2. 이 답변이 캐시됨 — **그런데 `sources=[]` → `source_files=[]`**
3. 관련 문서 업로드 → **어떤 파일과도 연관 안 돼 있어서 무효화 대상이 아님**
4. 같은 질문 재입력 → 여전히 캐시에서 "찾을 수 없습니다" (0ms)

**빈 의존성을 가진 캐시가 영원히 살아남는 "좀비 캐시"** 가 된 겁니다.

**[조정 — 15초]**
두 단계로 해결했습니다.
- **즉시 조치**: `answerable=false`인 답변은 **캐시 저장 자체를 건너뜀**
  - 근거: 거절은 "현재 문서 상태 기준"이지 영구 진실이 아님
- **근본 조치**: 문서 업로드 시 **전체 QA 캐시 삭제**
  - 근거: 문서 업로드 빈도 << 질의 빈도 → 재빌드 비용 낮음. 엣지 케이스 없음.

**[결과 — 10초]**
파일별 추적보다 코드가 더 단순해졌고, 검증 가능해졌습니다.
"완벽한 설계보다 엣지 케이스 없는 설계가 낫다"를 경험했습니다.

### 💡 일반화 가능한 교훈
- **캐시 무효화는 "캐시 키의 의존성"을 먼저 설계해야 한다.** 나중에 붙이면 좀비 캐시가 생긴다.
- **빈 의존성(`sources=[]`)을 가진 캐시는 무효화 불가능하다.** — 저장하지 말거나 전체 무효화.
- "이게 이론적으로 가능한가" 보다 "우리 도메인에서 빈도가 어떤가"로 설계를 결정하자 (업로드 < 질의).

### 🎤 슬라이드 구성 (2장)

**슬라이드 A: "좀비 캐시 시나리오"**
- 제목: 빈 의존성이 만든 좀비 캐시
- 시퀀스 다이어그램: ① 질문 → "찾을 수 없음" 캐시 → ② 문서 업로드 → ③ 재질문 → 여전히 "찾을 수 없음"
- 🧟 이모지나 비주얼 하이라이트

**슬라이드 B: "전체 무효화 선택"**
- 좌측: 파일별 추적 방식의 복잡성 (다이어그램)
- 우측: 전체 무효화의 단순성 (코드 3줄)
- 하단: `업로드 빈도 << 질의 빈도` 가정을 명시

### ❓ 예상 질문 & 답변

**Q1. "수천 개 문서를 운영하는 실무 환경에서도 전체 무효화가 괜찮나요?"**
A. 도메인에 따라 다릅니다. 문서 업로드가 질의보다 훨씬 적은 환경(사내 정책 문서, 매뉴얼 등)에서는 전체 무효화가 합리적입니다. 하지만 문서가 빈번히 추가되는 환경에서는 **Corpus 버전 태깅** 방식으로 개선해야 합니다 — Redis에 `corpus:version` 키를 두고, 캐시 엔트리에 버전을 태깅. 읽을 때 버전 불일치면 lazy invalidation. 이 개선안은 ARCHITECTURE 10장에 로드맵으로 기록했습니다.

**Q2. "캐시 히트율을 측정했나요?"**
A. 정량 측정은 하지 않았습니다. 이게 아쉬운 부분인데, 프로덕션이면 Redis INFO로 `keyspace_hits/misses` 비율을 모니터링해야 합니다. 현재는 응답의 `cached: true/false` 필드로만 개별 확인이 가능합니다.

**Q3. "유사 질문 캐시의 cosine 0.95 임계값은 어떻게 결정했나요?"**
A. 솔직히 말씀드리면, 실험적으로 확정한 수치는 아닙니다. 0.9는 너무 느슨해서 다른 의도의 질문이 히트될 위험, 1.0은 사실상 정확 일치와 같음 — 중간값인 0.95로 시작했습니다. 튜닝하려면 "의미상 같은 질문 쌍"을 라벨링해 precision/recall을 측정해야 하는데, 8일 기한 내 우선순위에서 밀렸습니다. 평가 하네스에 유사 질문 케이스를 추가해 측정하는 것이 다음 스텝입니다.

**Q4. "answerable=true 답변도 새 문서 추가 시 stale해질 수 있지 않나요?"**
A. 정확한 지적입니다. 그래서 근본 조치를 **전체 무효화**로 확장한 겁니다 — 새 문서에 더 정확한 정보가 있을 수 있으니까요. answerable=false 미저장은 좀비 캐시 방지용이고, 전체 무효화는 stale 데이터 방지용입니다. 둘이 역할이 다릅니다.

## 스토리 ③ — "자동 평가와 사용자 체감은 다르다"

### 🎯 한 줄 훅
> "숫자로는 Codex가 이겼는데, 제가 쓰는 입장에서는 Claude를 쓰고 싶었습니다."

### 📐 스토리 (60~90초)

**[가설 — 10초]**
기술 선택을 직감이 아닌 데이터로 하고 싶어서 **평가 하네스부터 만들었습니다**.
50케이스 × 7메트릭. 초기 20케이스에서 모델 차이가 안 나와서 50으로 확장했습니다.

**[실패 — 25초]**
결과는 명확했습니다 (v2 프롬프트 기준):

| 메트릭 | Claude | **Codex** |
|--------|--------|----------|
| Refusal Accuracy | 83% | **100%** |
| Latency p50 | 10.8초 | **4.5초** (2.4배 빠름) |
| JSON Parse | 100% | 100% |

데이터상 Codex 압승이었고, 실제로 Codex로 기본 설정했습니다.
그런데 웹 UI에 둘을 붙여놓고 **같은 질문 5개를 비교**해봤습니다.
- Claude: 번호, 불릿, 볼드로 **구조화된 답변**
- Codex: **1~2줄 평문**

정답률은 같은데, **"답변을 어떻게 받고 싶은지"** 의 차이가 있었습니다.
사용자가 매일 본다고 생각했을 때, 제가 선택하고 싶은 건 Claude였습니다.

**[조정 — 20초]**
한 단계 남아 있었습니다. Claude의 Refusal 83%를 해결해야 했습니다.
(→ 이 부분이 스토리 ①의 v3 프롬프트 작업이었습니다.)
Few-shot + 동의어 금지 + 이중 방어 적용 → Claude Refusal **100%** 달성.
이 시점에서 Claude는 **속도 제외 모든 영역에서 Codex 이상**이 됐습니다.

**[결과 — 10초]**
속도 차이(8.8초 vs 4.5초)는 **캐시 hit 시 0ms + SSE 스트리밍**으로 체감 지연을 보완했습니다.
최종: 기본은 Claude, 속도가 필요하면 `.env` 한 줄로 Codex로 전환.

### 💡 일반화 가능한 교훈
- **자동 평가는 정답률만 본다. 사용자 경험은 보지 못한다.** 정답률이 같다면 UX가 결정타.
- **평가 지표를 모르는 게 아니라, 평가 지표 외의 것을 놓치는 게 위험하다.**
- **데이터와 체감을 함께 봐야 한다** — 둘 중 하나만으로는 틀린 결정을 할 수 있다.
- (부수 교훈) 기술 선택을 데이터로 했다는 건 강점. 다만 평가 대상을 사전에 넓게 잡아야 한다.

### 🎤 슬라이드 구성 (2~3장)

**슬라이드 A: "평가 결과는 Codex 우위였다"**
- 제목: 숫자로는 Codex가 이겼다
- v2 비교 표 (위와 같은 형태, Codex 열 강조)
- 하단 결론: "→ 기본 설정: Codex"

**슬라이드 B: "UI 비교: 같은 질문, 다른 경험"**
- 좌측: Claude 답변 스크린샷 (번호/불릿/볼드)
- 우측: Codex 답변 스크린샷 (평문 1~2줄)
- 같은 질문을 캡션으로
- `eval/images/Q_1_pypdf-claude.png` vs `eval/images/Q_1_pypdf-codex.png` 활용

**슬라이드 C: "최종 선택 — Claude (+ Codex 옵션)"**
- v3 적용 후 지표 (Refusal 100% 도달)
- 아키텍처 설계: `LLMProvider` 인터페이스 + 2개 어댑터
- `.env` 한 줄 전환 코드

### ❓ 예상 질문 & 답변

**Q1. "평가 지표에 '답변 구조화 품질' 같은 걸 추가할 순 없었나요?"**
A. 매우 좋은 지적입니다. 가능합니다 — 예를 들어 "답변에 불릿/번호가 있는가", "길이가 적정한가" 같은 heuristic 지표, 또는 LLM-as-judge로 두 답변을 비교시키는 방법이 있습니다. 8일 기한 내에서는 자동화하지 못했고 눈으로 비교했습니다. 다음 스텝으로 생각하고 있습니다.

**Q2. "Codex를 왜 남겨뒀나요? 아예 Claude로만 가도 되지 않나요?"**
A. 두 가지 이유입니다. (a) Codex의 속도(2.4배)가 필요한 시나리오 — 예를 들어 실시간성이 중요한 챗봇이나 대화형 인터페이스. (b) 벤더 락인 회피 — SDK 하나에 종속되면 계약, 가격 변동, 서비스 중단에 취약합니다. `LLMProvider` 인터페이스로 추상화한 덕분에 `.env` 한 줄 변경으로 전환 가능합니다.

**Q3. "UI 비교를 5개 질문만 했으면 샘플이 작은 거 아닌가요?"**
A. 맞습니다. 샘플이 작아서 일반화 주장은 할 수 없습니다. 다만 차이가 매우 일관적이었고(5/5 모두 Claude가 구조화), 이건 모델 특성 차이(Claude의 helpfulness 성향)로 설명 가능했습니다. 더 엄밀히 하려면 double-blind 비교를 했어야 합니다.

**Q4. "처음부터 Claude로 선택하고 결정이 바뀌었다면 데이터 기반이 아니라 직감 기반 아닌가요?"**
A. 결정이 바뀐 게 아니라 **평가 기준이 확장**된 겁니다. 처음 기준은 "정확도 + 속도"였고, UI 비교로 "답변 구조화/가독성"이 기준에 추가됐습니다. 원래 기준 내에서는 Codex가 계속 우세했고, 기준이 넓어져서 Claude가 우세해진 거죠. 배운 점은 **평가 기준을 처음부터 포괄적으로 설계해야 한다**는 것입니다.
