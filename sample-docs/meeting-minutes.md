## 안건 1: Java 21 마이그레이션 일정

### 논의 내용
현재 order-api, payment-service, user-service가 Java 17에서 운영 중이다.
Java 21 LTS로 마이그레이션을 진행해야 하며, Virtual Thread 도입으로 동시 처리 성능 개선이 기대된다.

김철수: "Virtual Thread를 order-api에 먼저 적용하고 성능 비교 데이터를 확보하자."
이영희: "payment-service는 PG 연동 부분에서 blocking I/O가 많아 효과가 클 것 같다."
장호석: "CI/CD 파이프라인에서 Java 21 빌드 테스트를 먼저 추가해야 한다. Gradle 8.5 이상 필요."

### 결정 사항
1. **1차 (4월)**: order-api를 Java 21로 마이그레이션 + Virtual Thread 적용
2. **2차 (5월)**: payment-service, user-service 마이그레이션
3. **전제 조건**: Gradle 8.5 업그레이드 + CI/CD 파이프라인 수정 (장호석 담당, 3월 말까지)
4. **성능 비교**: 마이그레이션 전후 TPS, p95 latency 측정 (이영희 담당)

### 미결 사항
- inventory-service(Go)는 마이그레이션 대상 아님 (별도 논의 불필요)
- search-service(Python)의 Java 전환 여부 → 다음 분기 재논의

## 안건 2: 데이터베이스 성능 개선

### 논의 내용
order_items 테이블이 2억 건을 초과하여 주문 조회 API 응답시간이 p95 450ms로 악화되었다.
목표: p95 200ms 이하.

최정은: "파티셔닝을 적용해야 한다. created_at 기준 월별 Range 파티셔닝을 제안한다."
이영희: "현재 주문 조회 API의 80%가 최근 3개월 데이터만 조회한다."
김철수: "파티셔닝 외에 읽기 전용 레플리카를 추가하는 건?"
최정은: "레플리카는 이미 2대 운영 중이다. 문제는 테이블 크기 자체."

### 결정 사항
1. **order_items 테이블**: created_at 기준 월별 Range 파티셔닝 적용
2. **마이그레이션 방식**: pg_partman 사용, 서비스 무중단 (기존 테이블 → 파티션 테이블 전환)
3. **일정**: 스테이징 4월 1주 → 프로덕션 4월 3주 (최정은 담당)
4. **아카이빙**: 1년 이상 된 주문 데이터 → 콜드 스토리지 이동 (분기별 자동화)
5. **모니터링**: 파티셔닝 전후 쿼리 성능 비교 대시보드 생성 (장호석 담당)

### 미결 사항
- payments 테이블도 1.5억 건에 도달 중 → 5월에 동일 방식 적용 검토
- 아카이빙된 데이터 조회 API 필요 여부 → 비즈니스팀 확인 필요

## 안건 3: 보안 감사 결과 대응

### 논의 내용
2월 외부 보안 감사에서 지적된 3건에 대한 대응 방안 논의.

#### 지적 1: API Rate Limiting 미비
현재 api-gateway에서 전체 IP 기준 1,000 req/min만 적용 중.
사용자별 제한이 없어 인증된 사용자가 과다 호출 가능.

한지수: "사용자별 100 req/min, 미인증 사용자 30 req/min으로 차등 적용 필요."
김철수: "기존 고객 중 배치 호출하는 곳이 있는데, 사전 공지 필요하다."

#### 지적 2: 로그에 PII 포함
notification-service 로그에 고객 이메일, 전화번호가 평문으로 기록되고 있음.

한지수: "로그 마스킹 라이브러리를 도입하거나, 구조화 로그에서 PII 필드를 필터링해야 한다."
이영희: "Python logging에 커스텀 필터를 추가하면 된다."

#### 지적 3: 내부 서비스 간 통신 인증 부재
서비스 간 gRPC/HTTP 호출에 인증이 없어 네트워크 침투 시 무제한 접근 가능.

장호석: "Istio mTLS를 도입하면 서비스 메시 레벨에서 해결된다."
한지수: "Istio 도입 전까지 임시로 API Key 기반 인증을 추가하는 건?"
김철수: "Istio가 맞는 방향이다. 4월에 스테이징부터 적용하자."

### 결정 사항
1. **Rate Limiting**: 사용자별 100 req/min + 미인증 30 req/min (한지수 담당, 3월 말)
   - 배치 고객 예외 처리: API Key별 별도 한도 설정 가능
2. **PII 마스킹**: notification-service 로그 필터 추가 (이영희 담당, 4월 1주)
   - 이메일: `u***@domain.com`, 전화번호: `010-****-1234` 형식
3. **서비스 간 인증**: Istio mTLS 도입 (장호석 담당)
   - 스테이징: 4월 → 프로덕션: 5월
   - 임시 조치 없이 Istio 일정에 맞춤

### 미결 사항
- 보안 감사 대응 완료 보고 기한: 6월 30일 (한지수 → 경영진 보고)
- Istio 도입 시 서비스 성능 영향 → 스테이징에서 벤치마크 필수

## 안건 4: 프론트엔드 기술 스택 전환

### 논의 내용
현재 프론트엔드가 Vue 2 + Vuetify 2로 되어 있는데, Vue 2가 EOL(2023-12-31) 되었다.

박민수: "Vue 3 + Vuetify 3으로 전환하거나, React + MUI로 전면 재작성하는 두 가지 선택지가 있다."
김철수: "전면 재작성은 6개월 이상 걸린다. 기능 개발이 멈추는 건 받아들일 수 없다."
박민수: "Vue 3 마이그레이션은 Composition API 전환만 하면 3개월 정도."
이영희: "백엔드 API는 그대로니까 프론트만 변경하면 된다."

### 결정 사항
1. **Vue 3 + Vuetify 3 마이그레이션** 확정 (React 전환 기각)
2. **일정**: 2분기 (4~6월), 페이지 단위 점진적 마이그레이션
3. **우선순위**: 주문 관리 → 대시보드 → 고객 관리 → 설정
4. **병행 운영**: Vue 2/3 동시 빌드 (마이크로 프론트엔드 방식은 과도 → 라우트 기반 분리)

### 미결 사항
- 디자인 시스템 리뉴얼도 함께 진행할지 → 박민수가 디자이너와 논의 후 결정
- E2E 테스트 프레임워크: Cypress → Playwright 전환 여부 → 4월 PoC 후 결정
