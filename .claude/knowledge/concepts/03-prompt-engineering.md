# 03. 프롬프트 엔지니어링

> LLM에게 "원하는 답"을 안정적으로 받아내기 위한 입력 설계 기법. 이번 과제 평가의 15%를 직접 차지하고, RAG 품질 25%에도 영향을 줍니다.

## 1. 프롬프트 엔지니어링이란

**프롬프트(prompt)** = LLM에게 보내는 입력 문자열.
**프롬프트 엔지니어링** = 그 입력을 잘 설계해서 출력 품질·일관성·안전성을 끌어올리는 작업.

흔한 오해부터 풀고 가면:

| 오해 | 진실 |
|---|---|
| "좋은 모델이면 프롬프트 대충 써도 잘 답한다" | 같은 모델도 프롬프트에 따라 출력 품질이 2~3배 차이남 |
| "프롬프트는 마법 주문이다 (잘 쓰면 신기한 일이 일어남)" | 공학이다. 측정·반복·개선의 사이클이 핵심 |
| "한 번 잘 짜면 끝" | 모델 버전이 바뀌면 같은 프롬프트가 갑자기 망가질 수 있음 |
| "긴 프롬프트가 좋다" | 길수록 핵심이 묻힘. 토큰 비용도 ↑ |

## 2. 프롬프트의 구조

LLM에게 보내는 메시지는 보통 **3종류의 역할(role)**로 구성됩니다.

```
┌─────────────────────────────────────────────┐
│ system  : 모델의 페르소나/규칙 (변하지 않음) │
├─────────────────────────────────────────────┤
│ user    : 사용자 입력 (질문)                │
├─────────────────────────────────────────────┤
│ assistant : 모델의 답변 (이전 턴이 있을 때) │
└─────────────────────────────────────────────┘
```

### system 메시지 — 가장 중요
- "너는 누구이고 어떻게 행동해야 하는지" 정의
- 한 번 설정하면 대화 내내 유지
- **여기에 제약 조건을 박아두는 게 환각 억제의 핵심**

예시:
```
당신은 회사 정책 문서를 답변하는 도우미입니다.
다음 규칙을 반드시 따르세요:
1. 제공된 문서에서만 답을 찾아 답변하세요.
2. 문서에 없는 내용은 "문서에 해당 내용이 없습니다"라고 답하세요.
3. 답변에 반드시 [출처: 파일명] 형식으로 출처를 명시하세요.
4. 답변은 한국어로, 간결하게 작성하세요.
```

### user 메시지 — 동적 부분
- 사용자 질문 + RAG 검색 결과 + 추가 컨텍스트
- 매 호출마다 달라짐

## 3. RAG 프롬프트 — 우리 과제의 핵심

RAG 답변 생성 단계의 프롬프트는 **system + (context + question)** 구조로 갑니다.

### 표준 RAG 프롬프트 템플릿

```
[system]
당신은 회사 문서를 기반으로 답변하는 도우미입니다.
규칙:
1. 아래 <문서> 안의 내용으로만 답하세요.
2. 문서에 없는 내용은 "문서에 해당 내용이 없습니다"라고 답하세요.
3. 답변 끝에 [출처: 파일명, 청크번호] 형식으로 출처를 명시하세요.
4. 추측하지 마세요. 사실만 말하세요.

[user]
<문서>
[1] (출처: company-policy.txt, chunk_3)
연차 휴가는 입사 1년 미만은 매월 1일 발생, 1년 이상은 연 15일 발생합니다.
근속 2년마다 1일 추가, 최대 25일까지 가능합니다.

[2] (출처: company-policy.txt, chunk_4)
연차는 당해 연도 내 사용이 원칙이며, 미사용 연차는 이월되지 않습니다.
</문서>

<질문>
입사 3년차 직원의 연차는 며칠인가요?
</질문>
```

이 프롬프트의 설계 의도:

| 요소 | 의도 |
|---|---|
| `<문서>`/`<질문>` 태그 | LLM이 어떤 부분이 컨텍스트이고 어떤 부분이 질문인지 명확히 구분 |
| 각 청크 앞 `[1]`, `[2]` 번호 | 답변에서 인용할 때 이 번호로 참조 가능 |
| `(출처: 파일, 청크번호)` | 인용 정보 명시 |
| system의 "추측 금지" | 환각 억제 |
| system의 "없으면 없다고 답해" | 거절 강제 |

## 4. 핵심 기법

### 기법 1. **명확한 지시 (Clear Instructions)**
- 모호한 표현 금지: "잘 답해" (X) → "한국어로, 3문장 이내로, 출처 포함하여 답해" (O)
- 형식을 구체적으로: "JSON으로", "마크다운 표로", "번호 매긴 리스트로"

### 기법 2. **Few-shot 예시 제공**
- LLM에게 "이런 식으로 답해" 예시를 1~3개 보여주면 일관성 ↑
- 비용은 토큰 ↑

```
[system] ... 답변 예시 ...

예시 1:
질문: 재택근무 가능 일수는?
답변: 주 2회까지 재택근무가 가능합니다. 단, 팀장 승인이 필요하며 전사 캘린더에 등록해야 합니다. [출처: company-policy.txt]

예시 2:
질문: 화성 지사 주소는?
답변: 문서에 해당 내용이 없습니다.

위 예시처럼 답해주세요.
```

### 기법 3. **Chain-of-Thought (CoT) — 단계별 사고**
- "단계별로 생각하고 답해" 라고 지시
- LLM이 추론 과정을 출력 → 최종 답이 더 정확해짐
- 단점: 토큰 ↑, 응답 시간 ↑
- RAG에서는 보통 **CoT를 답변에 포함하지 않음** (사용자에게 노이즈)

### 기법 4. **출력 형식 강제 (Structured Output)**
- JSON, 마크다운 표, 특정 키워드 등으로 형식 박기
- LLM은 자유 텍스트보다 구조화된 출력을 더 일관되게 생성

```
다음 JSON 형식으로만 응답하세요:
{
  "answer": "답변 텍스트",
  "sources": ["파일명#chunk_id", ...],
  "confidence": "high|medium|low",
  "answerable": true|false
}
```

→ 우리 과제 평가 항목 "**LLM API 활용 — 구조화된 출력**"의 핵심.

### 기법 5. **역할 부여 (Role Assignment)**
- "당신은 [역할]입니다" 패턴
- 예: "당신은 회사 정책 전문가입니다", "당신은 정확성을 중시하는 사실 확인자입니다"
- 효과는 모델마다 다름. 보수적 페르소나가 환각 억제에 약간 도움

### 기법 6. **부정 명령 (Negative Constraints)**
- "~하지 마세요"가 "~하세요"보다 강하게 작동하는 경우가 있음
- 단, **모델이 부정을 무시할 수도** 있어 긍정형으로 대체할 수 있으면 그게 더 안전
- 예: "추측하지 마세요" → "오직 문서에 있는 내용만 말하세요" (긍정형)

## 5. 환각 억제 (Hallucination Suppression) — RAG의 생사

LLM은 모르는 걸 모른다고 안 하고 자신만만하게 거짓을 말합니다. 이걸 줄이는 기법 모음:

### 기법 H1. 강한 거절 지시
```
문서에 답이 없으면, 추측하지 말고 정확히 다음 문장으로 답하세요:
"제공된 문서에서 해당 내용을 찾을 수 없습니다."
```
- "정확히 이 문장으로" 가 핵심. 모호하게 두면 LLM이 마음대로 답함

### 기법 H2. 인용 강제
- "답변에 사용한 모든 사실은 [출처] 표기를 붙이세요"
- 인용을 못 붙이면 LLM이 "이걸 어디서 가져왔지?" 자기 검증을 함 → 환각 ↓

### 기법 H3. 사실 분리 + 추론 분리
```
답변 형식:
- 사실: 문서에 명시된 사실만
- 추론: (필요 시) 위 사실에서 끌어낸 결론
```
- 사실과 추론을 섞지 못하게 강제 → 추론 부분이 환각인지 명확

### 기법 H4. 컨텍스트 부재 처리
- 검색 결과가 0개거나 유사도가 낮으면 → LLM 호출 자체를 안 하고 "검색 실패" 응답
- 이건 프롬프트가 아니라 **파이프라인 레벨의 가드**

### 기법 H5. self-check (자기 검증)
- 답변 생성 후, 같은 LLM에게 "위 답변이 문서 내용과 일치하는지 검증해" 두 번째 호출
- 비용 2배. 정확도 향상은 케이스 바이 케이스
- 우리 과제: 시간 되면 시도, 안 되면 생략

## 6. 우리 과제에서 쓸 프롬프트 전략 (잠정)

**단계별 LLM 호출 분석**:

| 단계 | LLM 호출? | 프롬프트 전략 |
|---|---|---|
| 문서 청킹 | ❌ | 코드만 |
| 임베딩 | ❌ | 코드만 (sentence-transformers) |
| 벡터 검색 | ❌ | 코드만 |
| (선택) 쿼리 재작성 | ✅ | 짧은 system + 사용자 질문 → 검색용으로 변형된 질문 |
| (선택) Reranking | ✅ | 검색된 청크를 점수화 |
| **답변 생성** | ✅ | 위 4번의 RAG 표준 템플릿 |
| (선택) self-check | ✅ | 답변 검증 |

→ **답변 생성**이 가장 중요. 다른 단계는 옵션.

### 답변 생성 프롬프트 — 1차 초안 (1단계에서 다듬을 것)

```
[system]
당신은 사내 문서를 기반으로 직원의 질문에 답변하는 도우미입니다.

다음 규칙을 반드시 지키세요:
1. 답변은 오직 아래 <문서>에 포함된 내용만 사용하세요.
2. 문서에 없는 내용을 추측하거나 상식으로 보충하지 마세요.
3. 문서에 답이 없으면 정확히 다음과 같이 답하세요:
   "제공된 문서에서 해당 내용을 찾을 수 없습니다."
4. 답변은 다음 JSON 형식으로만 출력하세요:
   {
     "answer": "한국어 답변 텍스트",
     "sources": [{"file": "파일명", "chunk_id": 번호}],
     "answerable": true | false
   }
5. answerable이 false일 경우 sources는 빈 배열 [] 입니다.

[user]
<문서>
[1] (file: company-policy.txt, chunk_id: 3)
{청크 1 텍스트}

[2] (file: company-policy.txt, chunk_id: 4)
{청크 2 텍스트}
</문서>

<질문>
{사용자 질문}
</질문>
```

이 프롬프트의 설계 근거 (= `PROMPT_DESIGN.md`에 들어갈 내용):

| 요소 | 근거 | 평가 항목 |
|---|---|---|
| 강한 거절 지시 ("정확히 이 문장으로") | 환각 억제 H1 | 프롬프트 15% |
| JSON 구조화 출력 | 파싱 안정성 + 출처 기계 처리 | LLM 활용 20% (구조화) |
| `[1]`/`[2]` 청크 번호 | 인용 추적성 | RAG 25% |
| `answerable` 불린 | 거절 케이스 명시적 처리 | 평가 하네스의 Refusal 메트릭 |
| `chunk_id` 필드 | 문서 변경 시 캐시 무효화 키로 사용 | 캐싱 20% |

## 7. 프롬프트 엔지니어링 워크플로우

좋은 프롬프트는 한 번에 안 나옵니다. 다음 사이클을 반복합니다:

```
1. 가설 (이렇게 쓰면 좋을 것 같다)
        ▼
2. 작성
        ▼
3. 평가 하네스로 측정
   (Hit / Citation / Refusal / Latency)
        ▼
4. 실패 케이스 분석
   "왜 이 케이스에서 환각이 났지?"
        ▼
5. 프롬프트 수정
   (제약 추가, 예시 추가, 형식 변경)
        ▼
1로 돌아감
```

→ 평가 하네스가 없으면 이 사이클을 못 돔. 그래서 1단계 산출물이 평가 하네스 설계인 것.

## 8. 흔한 함정

### 함정 1. "프롬프트만 바꿨는데 다른 케이스가 깨졌다"
- 회귀(regression) 발생. 평가 하네스로 모든 케이스 다시 돌려야 발견 가능

### 함정 2. "사람한테는 명확한데 LLM이 못 알아듣는다"
- LLM은 **순서**, **태그**, **반복**에 민감. 사람이 보기에 똑같은 두 표현도 LLM에게는 다를 수 있음
- 해결: 측정 + 시행착오

### 함정 3. "system 메시지가 너무 길다"
- 토큰 비용 ↑, 그리고 모델이 후반부 지시를 무시할 가능성 ↑
- 핵심 규칙은 5개 이하로 압축

### 함정 4. "few-shot 예시가 데이터 분포와 다르다"
- 예시 1개가 잘못되면 LLM이 그 잘못된 패턴을 따라함
- 예시는 골든 데이터셋 케이스에서 직접 뽑기

### 함정 5. "JSON 강제했는데 모델이 가끔 마크다운 코드블록으로 감싼다"
- 일반적 현상. 파싱 단계에서 ` ```json ... ``` ` 래퍼를 벗기는 코드 필요
- Claude/GPT 둘 다 시스템 메시지에 "코드블록 없이 raw JSON만" 강조해도 가끔 어김

## 9. 우리 과제에서 다룰 프롬프트 엔지니어링 산출물

| 산출물 | 위치 | 내용 |
|---|---|---|
| `PROMPT_DESIGN.md` (필수) | 리포 루트 | 최종 프롬프트 + 설계 의도 + 평가 하네스 결과 표 |
| 프롬프트 템플릿 코드 | `app/prompts/` | jinja2 또는 python f-string 템플릿 |

## 10. 한 줄 요약

> **프롬프트 엔지니어링 = LLM에게 "원하는 답"을 안정적으로 받아내기 위한 입력 설계**.
> 핵심 무기는 (1) 명확한 제약, (2) 구조화 출력, (3) 강한 거절 지시, (4) 측정 기반 반복.
