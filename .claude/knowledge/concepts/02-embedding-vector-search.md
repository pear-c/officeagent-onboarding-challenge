# 02. 임베딩과 벡터 검색

> 이 문서는 RAG의 핵심인 "텍스트를 어떻게 검색하나"의 원리를 설명합니다. 수학 최소화, 직관 위주.

## 1. 풀어야 할 문제

키워드 검색(Elasticsearch, SQL `LIKE`)으로는 RAG가 잘 안 됩니다.

**예시**:
- 문서: "**연차 휴가**는 입사 1년 이상 시 연 15일이 발생합니다"
- 사용자 질문: "**휴가 일수**가 어떻게 되나요?"

키워드 검색은 두 문장을 **다른 것**으로 봅니다 ("연차"≠"휴가일수"). 하지만 의미는 같습니다.

→ 우리는 **"단어가 달라도 의미가 비슷하면 매칭되는 검색"**이 필요합니다.
→ 이게 **시맨틱 검색(semantic search)** = **벡터 검색**입니다.

## 2. 임베딩 — 텍스트를 좌표로 바꾸기

### 핵심 아이디어

**임베딩(embedding)**은 텍스트를 **고차원 공간의 좌표**로 변환하는 함수입니다.

```
"연차 휴가는 15일" ──[임베딩 모델]──► [0.12, -0.45, 0.89, ..., 0.33]  (768차원 벡터)
"휴가 일수"        ──[임베딩 모델]──► [0.10, -0.42, 0.91, ..., 0.31]  (비슷한 좌표!)
"파이썬 문법"      ──[임베딩 모델]──► [-0.55, 0.78, -0.20, ..., 0.04] (멀리 떨어진 좌표)
```

**좋은 임베딩 모델의 성질**:
- 의미가 비슷한 텍스트 → 좌표가 가까움
- 의미가 다른 텍스트 → 좌표가 멈

### 차원의 직관

768차원이라고 하면 어렵게 느껴지는데, **2차원으로 압축해서 시각화**하면 이렇게 됩니다:

```
       높음
        ▲
   휴가 │  연차
   일수 │
        │   (가까이 모임)
        │
        │
        │              파이썬
────────┼─────────────  문법    ─►
        │
        │              (멀리 떨어짐)
        ▼
       낮음
```

실제로는 768차원이지만 **"비슷한 건 가깝다"는 원리는 동일**합니다.

### 임베딩 모델은 어떻게 학습되나? (간단히)

수십억 개의 문장 쌍을 보여주면서:
- "이 두 문장은 비슷한 의미야" → 두 벡터를 가까이 끌어당김
- "이 두 문장은 다른 의미야" → 두 벡터를 밀어냄

이 과정을 수십억 번 반복하면, **의미적으로 가까운 텍스트는 자연스럽게 가까운 좌표**를 갖게 됩니다.

→ 우리는 학습 안 합니다. **이미 학습된 모델을 다운받아 쓰기만**.

## 3. 벡터 검색 — 가까운 좌표 찾기

### 거리 측정 방법

두 벡터가 "가까운 정도"를 수치로 표현하는 함수가 필요합니다. 보통 3가지를 씁니다.

| 방법 | 공식 (간단) | 직관 | 보통 사용 |
|---|---|---|---|
| **Cosine Similarity** | 두 벡터 방향이 얼마나 같은가 (-1~1) | 길이는 무시하고 방향만 봄 | **가장 흔함** |
| Dot Product | 두 벡터를 곱해서 합 | 길이도 함께 봄 | 모델이 normalize 되어 있으면 cosine과 같음 |
| Euclidean Distance | 직선 거리 | 일반적인 거리 감각 | 임베딩에는 잘 안 씀 |

**우리 과제**: cosine similarity 또는 dot product 사용. 임베딩 모델 문서에 권장 메트릭이 적혀 있음.

### 검색 알고리즘

벡터 DB에 100만 개 청크가 있다고 합시다. 사용자 질문 벡터와 가장 가까운 5개를 어떻게 찾을까요?

#### 방법 A. 무식하게 (Brute Force)
- 100만 개 모두와 거리 계산 → 정렬 → 상위 5개
- 정확하지만 느림 (큰 데이터셋에서)

#### 방법 B. 근사 최근접 이웃 (ANN, Approximate Nearest Neighbor)
- 미리 트리/그래프/해시 구조로 인덱스 구축
- 검색 시 일부만 비교 → 거의 정확한 답을 빠르게
- 알고리즘: **HNSW** (가장 흔함), IVF, ScaNN, Annoy 등

**우리 과제**: 샘플 문서 2개에서 청크 수십~수백 개 정도라 **둘 중 뭘 써도 0.01초**. 알고리즘 선택은 사실상 무관. 벡터 DB가 알아서 처리.

## 4. 청킹 (Chunking) — 임베딩 전 단계

임베딩하기 전에 문서를 **작은 조각**으로 잘라야 합니다. 이유:

### 왜 통째로 임베딩 안 하나?
- **임베딩 모델 입력 길이 제한**: 보통 512~8192 토큰
- **정확도 문제**: 긴 문서 한 덩어리를 임베딩하면 평균값이 되어 변별력이 떨어짐
- **검색 단위 문제**: "정확히 어느 부분이 답인지" 출처를 못 댐

### 청킹 전략 비교

| 전략 | 설명 | 장단점 |
|---|---|---|
| **고정 크기 (Fixed-size)** | N개 문자/토큰마다 자름 | 단순, 빠름. 단 문장 중간에서 잘릴 수 있음 |
| **문장 단위 (Sentence)** | 문장 끝(`.`, `?`)에서 자름 | 자연스러움. 문장이 매우 긴 경우 처리 필요 |
| **재귀 분할 (Recursive)** | 우선순위 구분자(`\n\n`, `\n`, `.`, ` `)로 단계적 분할 | 가장 흔한 방식. langchain 기본 |
| **시맨틱 청킹 (Semantic)** | 임베딩 유사도로 "주제 변화 지점" 찾아 자름 | 가장 정교, 비용 큼 |
| **마크다운 인식** | `##`, `###` 헤더 단위로 자름 | 마크다운 문서에 최적 |

### 청크 크기와 오버랩

청킹의 두 핵심 파라미터:

| 파라미터 | 의미 | 일반적 값 |
|---|---|---|
| `chunk_size` | 한 청크의 최대 길이 | 200~500 토큰 (한국어는 ~300자 권장) |
| `chunk_overlap` | 인접 청크 간 겹치는 부분 | chunk_size의 10~20% |

**오버랩이 왜 필요한가?**
- 청크 경계에 답이 걸쳐있을 수 있음
- 예: `[청크1: ...연차는 ] [청크2: 15일입니다...]` ← 둘 다 봐야 답
- 오버랩이 있으면: `[청크1: ...연차는 15일] [청크2: 연차는 15일입니다...]`

**우리 과제 추천**: chunk_size 300~500자, overlap 50~100자, 재귀 분할 또는 마크다운 인식 (sample-docs에 `.md` 파일이 있음).

## 5. 임베딩 모델 선택 — 우리 과제 관점

PRD가 `sentence-transformers` 같은 오픈소스를 명시. 한국어 지원이 필수입니다.

### 후보 모델 (한국어)

| 모델 | 차원 | 크기 | 한국어 | 특징 |
|---|---|---|---|---|
| `BAAI/bge-m3` | 1024 | 2.3GB | ⭐⭐⭐⭐⭐ | 다국어, 한국어 최상위, dense+sparse+multi-vector |
| `intfloat/multilingual-e5-large` | 1024 | 2.2GB | ⭐⭐⭐⭐ | 100개 언어, 안정적 |
| `intfloat/multilingual-e5-base` | 768 | 1.1GB | ⭐⭐⭐⭐ | 위의 작은 버전 |
| `jhgan/ko-sroberta-multitask` | 768 | 442MB | ⭐⭐⭐⭐ | 한국어 전용, 가벼움 |
| `BM-K/KoSimCSE-roberta` | 768 | 442MB | ⭐⭐⭐ | 한국어 전용, 오래됨 |
| `all-MiniLM-L6-v2` | 384 | 80MB | ⭐⭐ | 영어 위주, 한국어 약함 |

**1단계에서 결정 예정**. 잠정 후보: `BAAI/bge-m3` 또는 `intfloat/multilingual-e5-base` (성능과 크기 균형).

### 모델 선택 시 고려사항

| 항목 | 고려 |
|---|---|
| **차원 수** | 높을수록 정확하지만 저장공간/계산 ↑ |
| **모델 크기** | 큰 모델은 정확하지만 첫 다운로드 시간 ↑, 로딩 메모리 ↑ |
| **언어 지원** | 한국어 필수 |
| **라이선스** | 상업 이용 가능 여부 (대부분 OK) |
| **추론 속도** | CPU에서도 실용적인지 (GPU 없음 가정) |

## 6. 벡터 DB 선택 — 우리 과제 관점

### 후보

| DB | 타입 | 특징 | 우리 과제 적합성 |
|---|---|---|---|
| **Chroma** | 임베디드/서버 | Python 친화적, 가벼움, sqlite 백엔드 | ⭐⭐⭐⭐⭐ |
| **Qdrant** | 서버 | Rust로 작성, 빠름, 메타데이터 필터 강력 | ⭐⭐⭐⭐ |
| **Weaviate** | 서버 | 풍부한 기능, GraphQL | ⭐⭐⭐ (오버킬) |
| **Milvus** | 서버 | 대규모, 분산 | ⭐⭐ (오버킬) |
| **FAISS** | 라이브러리 | 메타 페북 작성, 인덱싱만 제공 (DB 아님) | ⭐⭐⭐ (직접 영속화 필요) |
| **pgvector** | PostgreSQL 확장 | 기존 RDB와 통합 | ⭐⭐⭐⭐ |
| **Pinecone** | 클라우드 SaaS | API 키 필요 | ❌ (제약 C3 위반) |

### 우리 과제 잠정 선택: **Chroma**

이유:
- Docker 컨테이너 한 줄로 띄울 수 있음 (`docker run chromadb/chroma`)
- Python 클라이언트 직관적
- 작은 데이터셋에서 충분히 빠름
- 임베디드 모드(파일 기반)도 지원 → 시드 스크립트와 궁합 좋음

→ 1단계에서 최종 결정.

## 7. 캐시에서의 벡터 검색 (보너스)

벡터 검색은 RAG 본 파이프라인뿐 아니라 **캐시 레이어**에서도 쓸 수 있습니다.

**유사 질문 캐시 패턴**:
1. 사용자 질문 도착 → 임베딩
2. **캐시 DB**에서 임베딩 유사도 0.95 이상인 과거 질문이 있는지 검색
3. 있으면 그 답변 즉시 반환 (LLM 호출 안 함)
4. 없으면 본 RAG 파이프라인 진행 후, 결과를 캐시에 저장

→ 채용 과제 요구사항 "동일/**유사** 질문 캐시"가 정확히 이걸 가리킴.
→ Redis는 `RediSearch` 모듈로 벡터 검색 지원 (또는 별도 작은 Chroma 인스턴스 사용).

## 8. 흔한 오해

### 오해 1. "임베딩 차원이 높을수록 무조건 좋다"
- 어느 정도까지는 그렇지만, 768→1024로 늘어나도 한국어에서 차이 작음
- 그 대신 저장공간/계산량이 늘어나 캐시 효율 저하

### 오해 2. "모델마다 임베딩이 호환된다"
- **절대 안 됨.** 모델 A로 색인 + 모델 B로 검색 = 쓰레기
- 모델 바꾸려면 **전체 재임베딩** 필요 → 모델 결정은 신중히

### 오해 3. "벡터 검색이면 키워드 검색은 필요 없다"
- 둘은 보완 관계. 정확한 코드명/숫자/고유명사는 키워드가 더 강함
- **하이브리드 검색**(벡터 + BM25) 패턴이 흔함. 우리 과제는 단순화 위해 벡터만 갈 가능성 큼

### 오해 4. "벡터 DB는 데이터 일관성을 보장한다"
- 대부분 벡터 DB는 **결과의 정확도(얼마나 진짜 가까운 거 찾았나)**가 보장 우선순위
- ACID 트랜잭션? 조인? 외래키? 기대 X. 그건 RDB의 영역

## 9. 한 줄 요약

> **임베딩 = 텍스트를 좌표로**, **벡터 검색 = 가까운 좌표 찾기**.
> 잘 만든 임베딩 + 적절한 청킹이 RAG 검색 품질의 90%를 결정한다.
