# 01. RAG 전체 개요

> 이 문서는 AI/RAG가 처음인 사람이 "RAG가 뭐고 왜 이렇게 만들었나"를 30분 안에 이해하도록 쓴 입문서입니다.

## 1. RAG란 무엇인가

**RAG = Retrieval-Augmented Generation** (검색 증강 생성)

LLM(Claude, GPT 등)에게 질문할 때, **답변의 근거가 될 문서를 먼저 검색**해서 LLM에게 함께 보여주는 방식입니다.

```
[일반 LLM 사용]
사용자 질문 ──────────────────────► LLM ──► 답변
                                      ↑
                               (학습 데이터로만 답변,
                                회사 내부 문서는 모름)


[RAG 사용]
사용자 질문 ──► 검색 시스템 ──► 관련 문서 청크들
                                      │
                                      ▼
                              "이 문서를 보고 답해줘"
                                      │
                                      ▼
                                     LLM ──► 답변 (출처 포함)
```

## 2. 왜 RAG가 필요한가

LLM은 강력하지만 다음 한계가 있습니다:

### 한계 1. 지식 마감일 (Knowledge Cutoff)
- LLM은 학습 시점까지의 데이터만 압니다
- 작년 회사 정책 개정? 모름
- 어제 올린 사내 문서? 모름

### 한계 2. 환각 (Hallucination)
- 모르는 걸 모른다고 안 하고 **그럴듯한 거짓말**을 함
- "회사의 연차는 20일입니다" — 실제로는 15일인데 자신만만하게 답변
- 채용 과제 PRD에 명시된 핵심 위험: "**환각 없이 적절히 처리해야 한다**"

### 한계 3. 출처를 댈 수 없음
- LLM 자체로는 "왜 그렇게 답했는지" 출처를 못 댐
- 회사 시스템에서는 "이 문서 어디에 그렇게 쓰여 있다"가 필수
- 채용 과제 PRD: "답변에는 **출처(어떤 문서의 어떤 부분에서 왔는지)**가 포함되어야 한다"

### 한계 4. 비공개 데이터
- 회사 내부 문서, 사내 정책, 고객 데이터는 LLM이 학습하지 않음
- 미세 조정(fine-tuning)은 비싸고 느리고 위험

→ **RAG는 위 4가지를 한 번에 해결**합니다. 검색으로 최신/내부 데이터를 가져오고, 그 안에서만 답하게 강제하면 환각이 줄고 출처도 명확해집니다.

## 3. RAG 파이프라인 — 두 단계

RAG는 시간상 분리된 두 개의 파이프라인으로 구성됩니다.

### 단계 A: Ingestion (수집/색인) — 문서를 미리 검색 가능한 형태로 만드는 과정

```
원본 문서 (PDF, TXT, MD, ...)
        │
        ▼
   ① 텍스트 추출
   (PDF → 평문, TXT → 그대로)
        │
        ▼
   ② 청킹 (Chunking)
   (긴 문서를 작은 조각으로 나눔)
        │
        ▼
   ③ 임베딩 (Embedding)
   (각 청크를 숫자 벡터로 변환)
        │
        ▼
   ④ 벡터 DB에 저장
   (벡터 + 원본 텍스트 + 메타데이터)
```

각 단계의 의미:

| 단계 | 무엇을 | 왜 |
|---|---|---|
| ① 추출 | 원본 파일에서 평문 텍스트만 뽑아냄 | LLM은 평문만 이해. 표·이미지·레이아웃은 별도 처리 필요 |
| ② 청킹 | 긴 문서를 200~500단어 조각으로 자름 | LLM에게 한 번에 보낼 수 있는 양이 제한적 + 검색 정확도 향상 |
| ③ 임베딩 | 각 청크를 768~1024차원 숫자 벡터로 변환 | 의미가 비슷한 텍스트끼리 벡터 공간에서 가까이 모임 → 검색 가능 |
| ④ 저장 | 벡터 DB에 색인 | 나중에 빠르게 "비슷한 거 찾기" 위해 |

### 단계 B: Query (질의응답) — 사용자가 질문할 때마다 실행

```
사용자 질문
    │
    ▼
① 질문을 임베딩
(같은 임베딩 모델로)
    │
    ▼
② 벡터 DB에서 유사 청크 검색
(질문 벡터와 가까운 상위 K개)
    │
    ▼
③ 검색된 청크 + 질문을 프롬프트로 조립
("아래 문서를 바탕으로 답해줘. 모르면 모른다고 해.")
    │
    ▼
④ LLM 호출
    │
    ▼
⑤ 답변 + 출처 반환
```

## 4. 우리 과제에서의 RAG 매핑

PRD의 4가지 핵심 요구사항을 RAG 단계로 매핑하면:

| PRD 요구사항 | RAG 단계 |
|---|---|
| 1. 문서 수집 (Ingestion) | 단계 A 전체 (추출 → 청킹 → 임베딩 → 저장) |
| 2. 질의응답 (Query) | 단계 B 전체 (검색 → 프롬프트 → LLM → 출처 포함 답변) |
| 3. LLM 응답 캐싱 | 단계 B 앞단에 캐시 레이어 추가 (질문 → 캐시 hit이면 LLM 안 부름) |
| 4. 프롬프트 설계 | 단계 B의 ③ "프롬프트 조립" 부분을 정성스럽게 |

## 5. RAG의 핵심 어려움 (= 우리가 풀어야 할 것)

채용 과제 평가 비중이 그대로 RAG의 어려움 순위입니다:

### A. 검색 품질 (RAG 25%)
- **청킹 전략**: 너무 잘게 자르면 맥락 잃음, 너무 크면 검색 정확도 떨어짐
- **임베딩 모델 선택**: 한국어 잘 되는 모델? 빠른 모델?
- **검색 개수(K)**: 3개? 10개? 너무 많으면 LLM이 헷갈림

### B. 답변 품질 (LLM 활용 20% + 프롬프트 15%)
- **출처 인용 강제**: "답변에 [문서명] 표기 필수"를 프롬프트로 강제
- **환각 억제**: "문서에 없는 내용은 '모른다'고 답해" 강제
- **구조화 출력**: JSON으로 답변+출처 분리해서 반환

### C. 캐싱 (캐싱 20%)
- **정확 일치 캐시**: 같은 질문은 LLM 안 부르고 즉시 반환
- **유사 질문 캐시**: "연차 며칠?" ≈ "휴가 일수가?" 같은 의미면 같은 답
- **무효화**: 문서가 바뀌면 그 문서를 참조한 캐시 다 지움

### D. BE 설계 (20%)
- 위 모두를 깔끔하게 레이어 분리
- 비동기 처리 (LLM 호출은 느림 → 다른 요청 막으면 안 됨)
- 에러 처리 (LLM 호출 실패, 벡터 DB 다운 등)

## 6. RAG의 변형들 (참고)

기본 RAG 외에 더 발전된 패턴들이 있습니다. 우리 과제는 **기본 RAG + 약간의 개선**이면 충분하지만, 면접에서 알면 좋음:

| 변형 | 설명 | 우리 과제에서 |
|---|---|---|
| **Naive RAG** | 위에서 설명한 기본 형태 | 베이스라인 |
| **HyDE** (Hypothetical Document Embeddings) | 질문을 LLM에게 "답변 가설"로 먼저 만들게 한 후, 그 가설을 임베딩해서 검색 | 질문이 짧을 때 검색 품질 향상. 추가 LLM 호출 필요 |
| **Reranking** | 1차 검색 결과를 다시 LLM/cross-encoder로 점수 매겨 정렬 | 정확도↑, 속도↓ |
| **Multi-Query** | 한 질문을 여러 표현으로 변형해 각각 검색 | 검색 누락 줄임 |
| **Agentic RAG** | LLM이 직접 "더 검색할까?" 판단하며 반복 | 복잡, 우리 과제 범위 밖 |

→ 우리는 **기본 RAG + Reranking 검토 + 캐시 강화** 정도로 갈 가능성이 큼. 1단계에서 결정.

## 7. 흔한 오해 풀기

### 오해 1. "RAG는 LLM을 똑똑하게 만든다"
- **아닙니다.** RAG는 LLM에게 **외부 정보를 보여주는 것**일 뿐. LLM 자체의 추론 능력은 그대로
- 즉, 검색 결과가 쓰레기면 답변도 쓰레기 (Garbage In, Garbage Out)

### 오해 2. "임베딩은 LLM이 만든다"
- 임베딩 모델과 답변 생성 LLM은 **다른 모델**입니다
- Claude/GPT 같은 답변 생성 모델은 임베딩 함수를 보통 따로 제공하지 않음
- → 우리 과제에서 임베딩은 `sentence-transformers` 같은 별도 라이브러리로 처리

### 오해 3. "벡터 DB가 똑똑하다"
- 벡터 DB는 그냥 "벡터 거리 계산이 빠른 데이터베이스"입니다
- 검색 품질은 **임베딩 모델**과 **청킹 전략**이 결정. 벡터 DB 종류는 거의 무관

### 오해 4. "RAG는 환각을 0으로 만든다"
- 줄여줄 뿐 0은 아닙니다. 프롬프트로 강하게 제약해도 LLM이 가끔 추측함
- 그래서 평가 하네스에서 "거절율"을 측정하는 게 중요
