# 08. 청킹 크기 트레이드오프

## 발견 (2026-04-10, 02-ingestion 테스트 중)

4,746자 마크다운 문서(`01-rag-overview.md`)를 chunk_size=400으로 청킹한 결과:
- **28개 청크** 생성 (기대: ~12개)
- 100자 미만 청크 10개 (최소 23자)
- 평균 156자 — chunk_size 400의 39%만 사용

### 원인

마크다운 인식 청킹이 **헤더별로 섹션을 먼저 분리** → 짧은 섹션도 무조건 별도 청크가 됨.
예: `### 한계 1. 지식 마감일` 아래 60자 내용 → 단독 청크.

## 청크가 너무 작으면 생기는 문제

### 1. 검색 정확도 저하 (가장 심각)

짧은 청크는 문맥이 부족해서 임베딩 벡터가 의미를 제대로 담지 못한다.

- 23자: "LLM은 근본적으로 아래 한계가 있습니다:" → 이 벡터로 뭘 검색할 수 있나?
- 질문과 매칭될 확률 낮거나, 엉뚱한 질문에 매칭됨

### 2. top-K 검색 시 노이즈

top-K=5로 검색하는데, 그 중 2~3개가 무의미한 짧은 청크이면:
- LLM에 전달되는 컨텍스트 품질 하락
- "다음에 읽을 문서" 같은 32자 청크가 상위에 올라오면 답변에 도움 안 됨

### 3. LLM 컨텍스트 낭비

- 짧은 청크: top-K=5 × 50자 = **250자** 컨텍스트
- 적절한 청크: top-K=5 × 350자 = **1,750자** 풍부한 근거
- 같은 top-K인데 전달되는 정보량이 7배 차이

### 4. 임베딩 비용/속도

- 28개 vs 15개 → 임베딩 호출 ~2배, Chroma 저장 벡터 수 증가
- bge-m3 기준 청크당 ~0.2초 → 28개 5.6초 vs 15개 3.0초

## 청크가 너무 크면 생기는 문제

- 관련 없는 내용이 섞여 검색 정밀도(precision) 하락
- top-K 결과가 중복 정보를 많이 포함
- LLM 컨텍스트 창 한계에 빨리 도달

## 최적 범위

| 크기 | 평가 |
|------|------|
| < 100자 | 너무 작음 — 문맥 부족, 노이즈 |
| 200~400자 | 적정 — 의미 단위 보존 + 검색 정밀도 |
| > 800자 | 너무 큼 — 불필요한 내용 혼입 |

## 개선 방향

마크다운 인식 청킹에서 **짧은 섹션 병합** 로직 추가:
- 인접 섹션이 합쳐도 chunk_size 이하면 병합
- 최소 청크 크기(예: 100자) 미만 섹션은 다음 섹션과 합침
- 섹션 경로는 병합된 청크에 첫 번째 섹션 경로 사용

기대 효과: 28개 → ~15개, 평균 크기 156자 → ~300자
